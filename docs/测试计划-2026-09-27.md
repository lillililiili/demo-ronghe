### 1.3 核心闭环：无人机事件处置（当前确认状态）

```
感知上报 → 目标融合 → 计划匹配与规则研判 → 告警事件 → 值班员核实
  → 自动通知链（短信→观察→电话→观察）→ 待反制 → 人工发起反制
  → 审批/直接执行 → 设备下发与回执 → 急停/核查 → 自动处罚移送 → 送达与签收 → 案件办理
```

**步骤与状态机（2026-09-22 用户确认口径）：**

1. **感知上报**：雷达/光电/5G-A/TDOA 等设备经 MQTT 上报，后端融合生成目标；来源区分 live/replay/mock，模拟数据必须明确标识。
2. **目标融合与计划匹配**：同一目标的多源观测按有效异步源组合融合，供飞行计划匹配。
3. **规则研判**：规则引擎按计划、空域、轨迹计算合法性结论与证据充分性（`decision_assurance`）。可靠明确结论直接展示，不要求人工复核；依据不足显示"核对信息缺口"。
4. **告警事件**：规则命中后生成告警事件，状态初始为「待核实」；**待核实期间不发短信**。
5. **值班员核实**（在告警页）：
   - 误报 → 不发短信、不进入待反制，记录并关闭；
   - 属实 → 进入自动通知链；
   - 无对应告警的研判才在合法性页核实。
6. **自动通知链**（核实属实后，由后端自动推进，不依赖页面）：
   - 有**已核验执行飞手**且短信通道可用 → 自动发短信，状态「自动短信」→ 送达后观察 10 秒，状态「观察中」；
   - 仍在告警空域 → 自动打电话，状态「自动电话」→ 播放完成后观察 10 秒，状态「观察中」；
   - 第二段观察结束仍未撤离 → 状态「待反制」，显示「发起反制」；
   - 没有已核验飞手，或短信通道不可用 → 核实后直接「待反制」；
   - 电话通道不可用 → 仍先自动短信 + 观察 10 秒，这段观察结束后才「待反制」；
   - 已离开 → 不打电话、不进待反制，列表仍显示告警已确认；
   - 短信已发出但没有新位置、无法确认是否撤离 → 不打电话，状态为「待反制」。
7. **反制（当前无自动反制规则，一律人工发起）**：
   - 入口：告警详情「手动反制」/「发起反制」，提交时后端校验资格（`can_direct_counter` / `can_request_counter`、当前有效观测、关联本事件、证据充分的明确违规研判）；
   - 有直接反制权限（`disposal:direct`，独立配置、默认无）→ 明确确认的直接反制表单；
   - 无直接授权 → 走申请审批流程，另一账号审批；
   - 执行设备必选（凌云 B、四通道），无人工执行通道，执行结果以设备回执为准；
   - 急停：执行中显示「急停本次处置」，未执行显示「撤销本次反制」；急停后现场停机核查，急停后不自动恢复授权。
8. **处罚移送（后端自动办理，前端只读进度）**：反制回执后自动移送；前端消费 `auto_handoff` 只读状态，不以打开页面触发交接；「移送与处罚」分别展示**送达状态**（待发送/送达待确认/已送达/发送失败）与**签收回执**（未进入签收/等待签收回执/已签收/回执超时），送达或签收不代表处罚办结。
9. **融合感知同步**：告警详情、融合感知、反制办理、合法性研判共用同一事件通知状态与视频入口（`GET /targets/{id}/video`，真实视频流未接通，模拟播放明确标识"非设备实拍"）。

### 1.4 分支流程

| 分支 | 流程 | 关键边界 |
| --- | --- | --- |
| 合法性自动研判 | 列表/统计只取 `object_type_code=UAV`；可靠明确结论无需人工复核；依据不足显示「核对信息缺口」；待处理 = 不可判定 ∪ 待复核 | 识别置信度不能替代合法性可靠性；旧记录可靠性未知如实显示 |
| 风险通知（飞行计划/空域/气象） | 待核验 → 核验通过 → 「通知上级」→ 送达与回执 | 只表示交接阶段，不代表风险解除；已通知/已排除隐藏核验操作 |
| 飞行计划设备检查 | 到时不飞 → 自动检查附近设备（5km）→ 异常 → 「通知设备异常」→ 后台运维待办 → 运维处理 | 设备正常 ≠ 允许起飞；运维处理 ≠ 设备恢复；疑似未起飞需报送单位确认 |
| 空域监测 | 空域列表 → 选中 → 风险/监测目标 → 光电追踪（有位置+权限+空闲设备）→ 模拟视频 | 纯气象风险不虚构追踪目标；模拟/接口模式分开，接口失败不回退模拟 |
| 飞行计划当前风险 | `/risks/current` 按有效时段分类，气象过期/缺依据标「待确认」 | 已通知/已签收不代表解除；完成/取消计划不展示 |
| 证据管理 | 预览/详情/保管/完整性检查 | 「检查文件完整性」≠ 内容真实；模拟/回放标识保留 |
| 运行统计 | 接业务事实：新增目标数（按首次发现去重）、立案数、处罚结果分布 | 缺失字段不补零，统计与 CSV 同源 |
| 信号模拟器 | 五组样本（沿计划偏航/禁飞区闯入/无计划/鸟群/设备故障）与外部接口收件箱 | 模拟记录不代表真实短信/电话/现场送达；收件箱只读 |
| 后台规则管理（自动/手动配置） | 后台「系统管理 → 规则管理」`/system/response-plans`：核实/反制/通知处罚三类规则配置与启停、生效设置、版本历史；原预案 `/system/response-plans/legacy` | 自动规则执行引擎未启用（`NOT_CONNECTED`），配置不触发自动动作；不靠规则开关控制人工按钮；反制授权仍由既有流程独立校验 |

### 1.5 权限与数据边界

- 页面可达性由服务端 `/auth/me` 的 `menu_keys` 决定，前端判断须与后端授权一致（E2E 已覆盖）；
- 动作权限示例：`risk:read`、`handoff:create`、`disposal:direct`、`disposal:stop`、`assessment:read` 等，均由后端校验，前端只做体验层；
- 数据范围：组织/区县元组（`owner_org_id, district_id`），越权详情与不存在统一 404；
- 飞手通知须短信与电话录音分渠道保存触发/发送/送达/播放及失败事实，一渠道成功不能替代另一渠道回执。
