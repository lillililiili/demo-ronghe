# 凌云回放数据集（MQTT 发布用）

给协作者 A 的 P1 联调用：`stage85-lingyun-demo.mqtt.ndjson` 是把我们阶段 8.5 的 v2 回放数据集
（`stage85-lingyun-demo`）导出成的可发布文件。**用任意 MQTT 客户端逐行发布，就能在平台侧复现 8.5 的全部场景。**
工参与 5G-A / 协议破解 / RemoteID 见同目录 `stage2-lingyun-static-dcd-rid.mqtt.ndjson`（12 行，不改本文件）。诱骗/干扰/驱鸟炮工参见 `stage3-lingyun-control-static.mqtt.ndjson`（3 行，无 SenseData）。

## 文件格式

NDJSON，一行一条待发布的报文，共 **180 行**：

```json
{"topic":"bridge/dongying/device_data/radar/S85R1","qos":1,"payload":"{...设备原文...}","record_no":0,"received_at":1757073600000,"source":"lingyun:radar:S85R1"}
```

| 字段 | 含义 |
| --- | --- |
| `topic` | 要发布到的 MQTT 主题 |
| `qos` | 固定 1（至少一次）。重复投递不会造成重复数据：平台侧以 `(source, source_msg_id)` 唯一键去重 |
| `payload` | **要发布的报文原文，是一个字符串** |
| `record_no` | 发布顺序号，从 0 递增 |
| `received_at` | 我们生成该报文时的时刻（epoch 毫秒），仅供对照，不必用它来控制发布节奏 |
| `source` | 平台侧的来源标识，用于对账；发布时不需要 |

> **`payload` 请原样发布，不要再做一次 JSON 序列化。**
> 它已经是设备会发出来的那段文本。把它解析成对象再重新序列化，键的顺序或空白会变，
> 平台侧算出的 `payload_hash` 就和我们这边对不上，联调时无法确认"两边跑的是同一份数据"。
> 用大多数客户端的写法就是：读一行 → 取 `payload` 这个字符串 → 作为消息体发到 `topic`。

## 主题

| 协议 | 主题 | 本数据集中的实例 |
| --- | --- | --- |
| A `SenseData` | `bridge/{providerCode}/device_data/{deviceTypeAbbr}/{deviceId}`，`providerCode` 用 `dongying` | `bridge/dongying/device_data/radar/S85R1`（84 行）、`.../tdoa/S85T1`（42 行）、`.../aoa/S85A1`（12 行） |

> 主题里的设备号（`S85R1` 等）是本数据集**虚构的回放设备号**，不对应任何真实设备；
> 报文体里的 `deviceId` 同理。发布时照用即可，不需要替换成真实设备号。
| C 光电跟踪上报 | `iot-reporting/cmlc/edge/{edgeId}` | `iot-reporting/cmlc/edge/S85E1`（42 行） |

## 发布顺序

**按 `record_no` 从小到大逐行发布即可。**

文件里有大量记录的 `received_at` 相同——同一帧里多路设备各报一条，本来就是同一毫秒。
**这些并列记录之间没有事实上的先后**，按 `record_no` 发布只是为了让每次联调都能复现同一个结果。
平台侧也不依赖同毫秒内的处理顺序（有专门的用例守着这条），所以你不必为并列记录设计特别的发送时序。

节奏上没有硬要求：可以尽快连发，也可以按 `received_at` 的相对间隔回放。

## 场景内容

前 6 个场景与阶段 8 的回放一致（三源同见、单源缺失、交叉、分裂合并、迟到乱序、精度差异），
另外 4 个是直连专有场景：

| 场景 | 看点 |
| --- | --- |
| `tdoa-pilot` | TDOA 带 `pilotLon/pilotLat`，平台侧会落到飞手位置列，供超视距判定使用 |
| `aoa-bearing` | AOA 报文里带经纬度，但按协议**无效**；平台侧只取 `extension.direction` 作方位，位置留空 |
| `eo-tracking` | 光电只在 `BeginTracking` 期间有观测，心跳不产生观测 |
| `identifying-255` | `objectType=255`（识别中），平台侧不给类别，只标记"识别中" |

## 空报文

协议 A 的 `objects: []`（本帧什么都没探到）是**合法报文**，平台侧照常受理并标记为已处理，不产生观测、也不计失败重试。
本数据集里没有这种记录，但你的适配器如果会把设备的空闲上报透传过来，不必特殊处理。

## 怎么核对两边拿到的是同一份数据

每行的 `payload` 与平台回放种子写进 `inbox_message.payload` 的内容**逐字一致**，因此：

```bash
# 取某一行的 payload 算 SHA-256
python3 -c "import json,hashlib,sys;p=json.loads(sys.stdin.readline())['payload'];print(hashlib.sha256(p.encode()).hexdigest())" \
  < stage85-lingyun-demo.mqtt.ndjson
```

把结果与平台侧同一条记录的 `payload_hash` 比对即可。

**注意 `source_msg_id` 在两条路径上不是同一个值：**

| 记录来自 | `source_msg_id` | 对账查询 |
| --- | --- | --- |
| 平台自己的回放种子 | 文件里的 `record_no` | `... AND source_msg_id = '0'` |
| 你经 MQTT 发布后由适配器写入 | 你的适配器按契约 §2 生成（协议 A 用 `ptTime:msgCnt`，协议 C 用 `timestamp:event:deviceId:taskId`） | 用你自己生成的那个键查，或直接按 `payload_hash` 反查 |

所以联调时**建议直接按哈希反查**，不依赖 `source_msg_id` 的写法：

```sql
SELECT source, source_msg_id FROM inbox_message WHERE payload_hash = '<你算出的 sha256>';
```

能查到，就说明你发出的报文与我们回放用的原文逐字一致。逐行一致这件事在平台侧由自动化用例
`LingyunMqttReplayExporterTest.payloadHashMatchesWhatTheReplaySeedWroteIntoInbox` 守着。

## 本机 Mosquitto 发布

仓库 `deploy/compose.yml` 提供只监听 `127.0.0.1:1883` 的 Mosquitto，给 local 联调用，不是现场 broker。
`local` profile 会登记连接 `local-lingyun-replay` 和设备 `S85R1`/`S85T1`/`S85A1`/`S85G1`/`S85D1`/`S85I1`/`S85E1D1`/`S85Y1`/`S85F1`/`S85B1`（光电外部编号是 `S85E1D1`，边端 `S85E1`；`S85G1` 为 5G-A，`S85D1` 协议破解，`S85I1` RemoteID；`S85Y1` 诱骗，`S85F1` 干扰，`S85B1` 驱鸟炮）。
**`S85R1` 不是 T02 TCP 雷达。** 六步与限制见 [server/README.md](../../server/README.md)「本地 MQTT 模拟」。

阶段 2 另有工参 + 5ga/dcd/rid 样例 `stage2-lingyun-static-dcd-rid.mqtt.ndjson`（12 行，含 `bridge/.../device/...` 工参）。阶段 3 控制类工参 `stage3-lingyun-control-static.mqtt.ndjson`（3 行）。**不要改**冻结的 180 行 8.5 文件；发布时显式 `--file`：

```bash
python server/scripts/publish_lingyun_ndjson.py --file docs/直连接入计划/stage2-lingyun-static-dcd-rid.mqtt.ndjson
python server/scripts/publish_lingyun_ndjson.py --file docs/直连接入计划/stage3-lingyun-control-static.mqtt.ndjson
python server/scripts/reply_lingyun_control.py
```

```bash
# 在仓库根目录；payload 按字符串原样发布，脚本不会再 json.dumps
python server/scripts/publish_lingyun_ndjson.py
# 缺依赖：pip install paho-mqtt
# 只校验不发送：python server/scripts/publish_lingyun_ndjson.py --dry-run --limit 5
```

inbox 里 `status=RECEIVED` 只说明适配器收下了报文。融合默认关；光电 `BeginTracking` 须先手点跟踪，否则不会入库。
不要改 `stage85-lingyun-demo.mqtt.ndjson`；要加场景就建新数据集 id。

## 已知与协议不符的两处（2026-09-10 实测）

对照 `设备资料/凌云协议/协议A-设备数据及感知数据接入协议v8.6.pdf` 与协议 C 的 PDF，本数据集有两处与协议不符，**都在数据集这一侧，平台的判断是对的**：

| 字段 | 协议规定 | 本数据集 | 回放后果 |
| --- | --- | --- | --- |
| 协议 A `msgCnt` | "对上报的数据进行连续的编号，来校验数据是否有丢失"——字段在每台设备自己的 `SenseData` 里，即**按设备各自连续** | 跨设备的全局计数器（雷达 0,3,6…，TDOA 1,4,7…，AOA 从 134 起） | 平台按设备判断断号，雷达报 53 次、TDOA 41 次、AOA 11 次"疑似缺报"，设备页直接显示 |
| 协议 C `taskId` | 平台手点跟踪时生成的 UUID 下发给光电，光电在 `BeginTracking` 里回显（协议示例即 `d0652e40-…`） | 写死的 `E-T1`（24 条）/ `E-L`（6 条）/ `T-EO-TRACK`（5 条） | 与平台任务号永远对不上，35 条全部 `TRACK_NOT_OPEN`，不管有没有手点跟踪 |

另有一处是数据集"太少"而不是"错"：协议 A 规定 **30 秒收不到工参判离线、真设备每 5–10 秒报一次**，本数据集每台设备只有一条工参且 `ptTime` 固定，重发会被判 `STALE_STATIC`。一次性回放后设备只在线 30 秒。

冻结文件不改。回放时用发布脚本的两个开关和保活脚本绕过（见 [server/README.md](../../server/README.md)「本地 MQTT 模拟」）：

```bash
python server/scripts/keepalive_lingyun_static.py                  # 另开终端一直跑：按协议节奏补发工参/心跳
python server/scripts/publish_lingyun_ndjson.py --eo-task-id <平台任务号> --renumber-msgcnt
```

`--eo-task-id` 默认只替换 `E-T1`（主跟踪场景 24 条，`--eo-task-id-for` 可改）。`E-L`（迟到乱序）和 `T-EO-TRACK`（自动跟踪）是另外两段跟踪，平台同一台光电同一时刻只允许一个进行中任务，不能一起替换成同一个号——三段会被当成同一条航迹，光电反而关联不上雷达。这 11 条在单次回放里仍会 `TRACK_NOT_OPEN`。

实测（2026-09-10，空库 + `--app.fusion.replay.seed-enabled=false` + `APP_FUSION_ENABLED=true`）：只靠 MQTT 发布，`目标-20250905-001` 融合出 光电+雷达+TDOA 三源，疑似缺报 0。

两个开关都会改 payload 字节，被改写记录的 `payload_hash` 不再与本文件一致；默认不开。要根治得建一个新的数据集 id 重新导出。

## 对账时 `source` 也不一样

上面的对账表只提醒了 `source_msg_id`。协议 A 的 `source` 两边也不同：本文件与平台回放种子写的是 `lingyun:radar:S85R1`（外部设备号），MQTT 适配器写的是 `lingyun:radar:<内部 device.device_id>`——这是 [device-direct-access-contract.md](../backend-stage8/device-direct-access-contract.md) §2.1 定的（内部 ID 才是同一台物理设备在 replay/live 下的稳定键）。协议 C 两边都是 `eo-edge:<edgeId>`。按哈希反查不受影响。

## 重新生成这个文件

导出器默认不启用（它只在本地按需生成仓库里的文档产物）。需要重新生成时：

```bash
java -jar server/target/low-altitude-server-0.1.0-SNAPSHOT.jar \
  --spring.profiles.active=local --app.dev-seed.enabled=false --app.replay.export.enabled=true \
  --spring.main.web-application-type=none
```

默认写到 `docs/直连接入计划/stage85-lingyun-demo.mqtt.ndjson`；
换路径加 `-Dapp.replay.export.target=<路径>`。数据集用固定随机种子生成，**重复导出内容逐字节一致**。

注：`local` profile 默认连本地 PostgreSQL（`jdbc:postgresql://127.0.0.1:5432/uav`）。
导出本身不读业务数据，但 Spring 启动需要可用的库；临时库也可以，加
`--spring.datasource.url=jdbc:postgresql://127.0.0.1:5432/<库名>` 即可。
