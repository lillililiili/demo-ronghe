# 合法性判定：算法自动判定与人工复核分流 Spec

确认日期：2026-09-17。

状态：用户确认需求后，已继续授权修改页面和算法。首版实现采用既有计划/空域/轨迹规则计算与新增证据充分性算法，后端保存分流结果，前端按结果展示人工入口；统计准确率尚未通过真实样本验证。实现与验证记录见本文末尾及实施计划。

## 用户确认的逻辑

系统将飞行计划的相关数据提供给算法，由算法自动推算并判定合法还是非法。

- 输入数据满足算法的推算条件，算法能够可靠、明确地给出“合法”或“非法”时，系统直接展示自动判定结果，右侧不显示“核对信息缺口”功能，不要求人工确认后才使该判定生效。
- 算法判定准确率不足、不能可靠给出明确结论时，右侧才显示“核对信息缺口”，进入人工复核。
- “核对信息缺口”就是人工复核，不是每条记录必须经过的常规步骤，也不是与人工复核并列的另一套流程。
- 明确判为非法与明确判为合法遵循同一原则：不能仅因为结果是“非法”，就要求人再次核对。
- 需求确认时用户说明目标算法尚未具备，随后授权本轮实现；不能把现有规则引擎、演示参数或本轮功能测试描述为统计准确率已验证。

“输入满足推算条件”表示足以支持判定，不等于自动判合法；同样可以依据充分的数据明确判非法。

## 输入与自动处理边界

沿用项目已确认的实际飞行研判范围：飞行计划相关数据与同一无人机的有效观测、实际轨迹、适用航线及空域规则共同作为判定依据。未执行计划仅有报备数据时，不能据此宣称实际飞行已经合法或非法。

| 环节 | 要求 |
| --- | --- |
| 触发数据 | 接收到相关计划、飞行观测或影响判定的依据更新后，由系统触发算法评估；具体触发事件与调度方式在算法接入时定义。 |
| 判定依据 | 由算法说明本次输入是否满足推算条件、能否明确判定、判定依据及不确定原因；前端不自行推算合法性或可靠程度。 |
| 数据时效 | 输入保留来源、版本和发生/观测时间；缺失、冲突、失效的数据不得默认视为满足判定条件。具体有效期由算法与业务契约确定。 |
| 自动动作 | 满足可靠判定条件时，保存并展示合法或非法的自动结果及依据，无需逐条人工复核；自动评估不依赖用户停留在页面。 |
| 人工介入 | 算法无法可靠判定时，展示“核对信息缺口”，说明具体缺失、冲突或不确定因素，复用人工复核流程。 |
| 失败处理 | 算法未接入、调用失败、结果缺失或可靠性未知时，明确显示实际状态，进入待处理分支；不得伪造明确结论、低置信度数值或成功状态。 |

## 右侧展示规则

| 算法输出情况 | 结论展示 | “核对信息缺口”功能 |
| --- | --- | --- |
| 可以可靠、明确地判为合法 | 展示合法、依据与更新时间 | 不显示，不要求人工复核。 |
| 可以可靠、明确地判为非法 | 展示非法、依据与更新时间 | 不显示，不要求人工复核。 |
| 有倾向性的合法/非法结果，但可靠程度不足 | 明确标识结果尚不能可靠确认，展示不确定原因 | 显示，供人工复核；不能因已有结论标签而隐藏。 |
| 缺少关键数据或存在冲突，算法无法明确判定 | 展示无法明确判定及信息缺口 | 显示，供人工复核。 |
| 算法未接入、调用失败或未提供可靠性判断 | 展示未接入、失败或结果不可用等真实状态 | 保留待处理说明；人工复核可用时显示入口，不能伪装成算法已运行但准确率低。 |

可靠自动判定分支中，不通过改名为“核对判定依据”“人工确认”等方式继续要求人工复核。结论依据、计划与轨迹对照仍可查看；原有复核历史继续保留。

需要人工复核时，是否有权提交仍由后端权限及状态决定；无权限用户可以看到待处理原因，但不能提交复核。前端隐藏按钮不代替后端业务分流。

## 可靠性口径与后续验证

用户已确认的是“能够可靠明确判定则自动采纳，可靠程度不足则人工复核”的业务分流。首版工程契约见后文；后续统计准确率验收与业务规则确认仍需实际样本依据，不以工程功能通过代替：

- 首版算法、输入质量门、接口字段与现有状态的兼容方式已按后文实现。
- 总体准确率、误判与漏判仍需带有权威结论的实际样本验证；功能测试不产生这些统计结论。
- 首版沿用版本化业务参数判断单次依据充分性，真实观测相关参数必须已确认；当前不预设 75%、90% 或 95% 等概率阈值。

风险高低和风险评分、目标识别/融合置信度、算法总体准确率与单次合法性判定可靠性分别表达，不能相互替代。不能只看 `legal_status`、是否允许 `REVIEW` 或是否存在任意未知字段，就推定本次必须复核或无需复核。

## 实施前差异（2026-09-17 需求确认时）

截至本次源码核对：

- 后端已有基于计划匹配、空域和飞行行为检查的规则引擎，并有目标置信度与轨迹质量门槛；这不等于目标算法及准确率验证已完成。
- 当前前端 `legalityReviewFocus.js` 主要结合已有结论、复核状态、权限及未知原因安排人工入口。未复核的非合法记录可能仍显示“核对判定依据”；合法记录也没有按目标算法的可靠性结果进行分流。
- 本需求补足的是算法是否能够可靠自动判定与人工复核之间的分流契约，不能只删除或隐藏当前按钮就声称完成。

本 Spec 对同一事项替代旧的展示原则：不再仅按“合法无需复核，非合法视复核状态处理”安排右侧功能；应按算法能否可靠明确判定分流。历史阶段报告保留为当时实现记录，不作为新需求的验收标准。

## 后续验收场景

以下是本轮实现必须验证的场景，实际结果在实施记录中分别注明：

1. 有效输入支持算法可靠判为合法：展示合法和依据，右侧没有“核对信息缺口”或等价人工确认要求。
2. 有效输入支持算法可靠判为非法：展示非法和依据，右侧同样没有人工复核要求。
3. 算法给出倾向性结果，但不能可靠确认：展示不确定性及“核对信息缺口”，合法/非法的倾向标签均不改变该分流。
4. 输入缺失、冲突或过期导致无法判定：如实显示原因，不补造数据或强行归为合法/非法。
5. 算法未接入或调用失败：显示真实可用性，不伪装成已运行结果，不编造准确率。
6. 人工复核保留原始算法结果、人工结论与说明；新数据触发重新判定后，列表和详情读取同一最新结果，刷新或重新进入页面不恢复过时的复核要求。

自动合法性判定不等于反制授权、通知送达、风险解除或处罚决定；这些业务继续遵守各自既有权限、授权与回执条件。

## 2026-09-17 首版工程实现

算法采用 `EVIDENCE_SUFFICIENCY_V1`：系统仍自动执行 C01 计划匹配、C02 空域/飞行行为检查和 C03 分类，再在同一研判事务中判断该结论是否具备足够依据。它输出证据充分性，不输出虚构的正确概率。

- `SUFFICIENT`：有效观测与轨迹质量合格；合法结果还须完整匹配计划身份并完成必要检查；非法结果须有明确的禁飞、空域限高或临管违规事实。按已配置规则不影响结论的其他未知项保留展示，不单独强迫复核。
- `INSUFFICIENT`：质量不足、身份线索缺失、仅凭无匹配计划推定无授权、必要检查缺失或无法形成明确二元结论等，保存具体原因。现有 `ABNORMAL` 风险状态保持原义，不批量改成非法。
- `NOT_APPLICABLE`：本次不适用实际无人机飞行判定，保留原原因，不制造人工复核任务。
- 旧记录没有这版算法结果时 API 返回 `UNAVAILABLE`；历史不回填、不改旧发生时间，重新研判产生新记录。

真实观测参与决策的参数须为已确认参数；模拟/回放可按演示参数验证流程，但仍保留来源标识。页面的“依据充分”仅指按当前规则与输入可明确判定，不表示经过统计校准的高准确率。

列表与详情增加 `decision_assurance`，包含算法版本、充分性状态、是否仍需人工复核、原因，以及 `accuracy_status=NOT_VALIDATED`。后端从同一持久化事实计算 `review_required`，与用户是否拥有提交权限分开；已复核、被取代、影子评估和不适用记录不重复进入待处理队列。`needs_review=true` 在分页前筛选真正需要处理的记录，包含低可靠的合法/非法结果及旧记录的未知结果。

右侧可靠结果隐藏人工任务区和主复核按钮；不足/未知结果显示“核对信息缺口”及原因，无操作权限时只读。算法暂不可靠的合法/非法标签追加“暂不能可靠确认”。自愿纠错保留在“更多操作”，原系统结论和人工历史均保留。

首版复用现有后台定时研判、回放、手动发起和重新判定入口；定时入口处理新到且仍有效的无人机观测，不依赖页面开启。仅更新计划资料、没有新观测时的独立事件触发尚未新增。新算法作用于新产生的研判记录；历史记录需重新判定生成新记录，不能修改旧算法事实。手动/重算沿用原有按观测时点评估的语义，结果及依据时间不代表当前仍满足飞行条件。
