# 无人机融合感知与低空安全管理平台整体改造方案

## 1. 结论摘要

当前系统不是“功能少”，而是“功能没有围绕用户完成一件事来组织”。项目已经具备较深的低空监管领域模型、跨模块数据关联、受控反制流程和数据一致性校验，但产品形态仍偏向演示驾驶舱：页面多、指标多、技术信息多，用户进入系统后仍需自己判断先做什么、去哪里做、何时算完成。

建议把改造目标从“继续补页面”调整为“让五类岗位在系统内完成闭环工作”，以统一事件工作台为主轴，以角色化工作台、任务与责任机制、真实数据与流程服务为三项基础工程。改造不建议推倒重写，应保留现有领域规则与数据断言，先重组用户入口和主流程，再逐步替换 legacy 页面与 Mock 数据层。

建议北极星指标：**可在系统内完整闭环的事件占比**。

## 2. 本次审计范围与证据

- 产品范围：融合感知、飞行监管、告警处置、处罚案件、证据管理、设备运维。
- 核心用户任务：发现异常 → 判断风险 → 告警核实 → 授权处置 → 案件办理 → 证据留存。
- 证据方式：在 1280×720 桌面视口下运行本地应用，逐步检查主要页面和反制授权弹窗；同时检查代码架构、权限实现、数据来源和验证脚本。
- 限制：未连接真实后端、真实设备、外部管控平台和真实账号，无法验证接口性能、多人协作、消息到达、生产权限隔离和真实文件下载；可访问性结论为可见风险，不代表完整 WCAG 合规测试。

| 步骤 | 用户任务 | 当前健康度 | 主要判断 |
|---|---|---:|---|

## 4. 当前系统的真实优势

1. **领域规则基础扎实。** Mock 数据不是简单写死数字，已经表达设备、目标、轨迹、告警、案件、授权、证据、飞行计划、空域和角色权限之间的关系。
2. **安全关键流程意识较强。** 反制授权包含目标确认、范围校验、合法目标影响、设备状态和人工双确认，适合作为生产流程的基础。
3. **数据口径治理优于一般演示系统。** 源码扫描通过；183 条断言配合 158 种注入，144/144 个必抓注入均被捕获。这部分应保留并升级为正式领域测试。
4. **跨模块追溯已经存在。** 告警可追到目标，案件可追到证据和授权，证据能反查引用对象，说明统一事件工作台不是从零开始。
5. **工程可运行。** Vue 生产构建通过，主要页面可正常访问，地图与图表在本地演示环境能够渲染。

## 5. 为什么领导会认为“整体应用性不高”

### 5.1 首页展示“系统看到了什么”，没有回答“我今天要做什么”

首页默认是融合感知地图，信息完整但面向所有人同一套展示。值班员、授权人、设备运维、审计员和领导的第一任务完全不同，当前都从同一菜单和同一管理员视角进入。

结果是用户把系统当作查询和展示工具，而不是工作入口。

### 5.2 信息架构按功能模块拆分，不按用户任务组织

同一事件被拆成目标编号、告警编号、案件编号、授权编号和证据编号。虽然数据层有关联，页面层仍要求用户在“融合感知 → 告警事件 → 处置与处罚 → 证据管理”之间跳转并重新定位。

系统应围绕“一件事”组织，而不是要求用户理解内部模块边界。

### 5.3 有状态，没有任务管理

当前页面大量展示“待核实、反制中、待处置、待通知、异常”等状态，但缺少生产系统必需的任务属性：

- 当前责任人和责任单位；
- 优先级与法定/业务时限；
- 已等待多久、是否超时；
- 下一动作、阻断原因；
- 转派、协办、催办和交接；
- 处理完成后的验收条件。

因此“看到了问题”与“推动问题解决”之间存在明显断层。

### 5.4 关键判断被大量技术细节包围

页面同时展示置信度、融合来源、轨迹点型、规则编号、空域参数、设备参数等专业信息。它们对复核很重要，但一线用户首先需要看到的是：

- 结论是什么；
- 为什么；
- 风险有多大；
- 系统建议做什么；
- 我现在能做什么；
- 做完后谁接手。

技术信息应作为“判定依据”按需展开，而不是和主动作争夺首屏注意力。

### 5.5 大量交互仍是 Demo 语义

项目唯一数据源是本地 `mock.js`；部分状态只写入内存或 `sessionStorage`；下载、导出、退出等动作多以 Toast 表示，真实文件、真实接口、持久化、多人并发和外部回执尚未形成生产闭环。

这会直接降低用户信任：用户不知道操作是否真正送达、是否可恢复、是否已被其他人处理。

### 5.6 前端角色权限已形成演示闭环，生产授权仍待后端承接

当前已将用户管理与角色管理拆分，角色可分别配置菜单权限和“查看 / 操作 / 授权”等级；侧栏、直达路由、顶栏身份和主要状态动作共用同一权限矩阵，并保留双人复核与操作审计。上述能力仍是本地 Mock 演示：真实账号、组织数据范围、敏感字段脱敏和 API 级授权尚未接入，不能替代生产环境的后端校验。

### 5.7 运维链路没有工单化

设备页已经把异常、离线置顶，但后续仍是查看、编辑、停用、跳实时监测。缺少故障建单、派发、到场、恢复、验证、关闭、复盘，无法衡量设备问题是否真正解决。

### 5.8 可访问性和屏幕适应存在风险

- 顶栏设置 `min-width: 1280px`，产品实质上是固定桌面工作台，窄屏和放大场景容易横向拥挤。
- 大量正文和辅助信息使用约 11–13px 字号，并存在多层内部滚动。
- 表格行被设为可聚焦，但多数页面只绑定点击，没有绑定 Enter/Space；侧栏分组和用户菜单也使用可点击 `div`，键盘语义不完整。
- 颜色承担较多状态含义，仍需真实对比度和色觉测试。

## 6. 目标产品形态

### 6.1 从六个功能模块，调整为六个用户任务中心

1. **工作台**：我的待办、值班态势、超时任务、最新交接、常用入口。
2. **事件中心**：所有目标、告警、研判、处置、案件、授权、证据围绕同一事件组织。
3. **飞行服务**：计划接收、预审、执行监控、偏离风险、上级通知。
4. **设备运维**：设备健康、异常工单、实时诊断、接入调测、恢复验收。
5. **分析审计**：运行成效、事件复盘、证据完整性、操作审计、监管报表。
6. **系统配置**：用户、角色、规则版本、数据源、接口与字典。

现有页面不必一次删除，可作为事件工作台和任务中心的子视图逐步收编。

### 6.2 五类角色拥有不同首页

| 角色 | 首页第一屏 | 核心动作 |
|---|---|---|
| 值班员 | 高风险新告警、待核实、即将超时、实时态势 | 核实、误报、升级、派单 |
| 指挥/授权人 | 待授权处置、合法目标影响、设备可用性、审批风险 | 批准、驳回、调整方式、急停 |
| 办案人员 | 待补证、待通知、待复核 | 补证、送审、通知、办结 |
| 设备运维 | 离线/异常设备、影响范围、未恢复工单 | 领单、诊断、维修、验证、关闭 |
| 领导/审计 | 闭环率、响应时长、积压、重大事件、审计异常 | 下钻、督办、导出、复盘 |

### 6.3 统一事件工作台

以“事件”为唯一主对象，首屏固定展示：

- 事件标题、等级、当前阶段、责任人、已持续时长；
- 系统结论、关键依据、可信度和不确定项；
- 下一步动作与阻断原因；
- 目标、告警、案件、授权、证据的关联数量；
- 从发现到结案的统一时间线；
- 地图、轨迹、视频和文书按标签页展开；
- 右侧固定操作区，按照当前阶段只显示可执行动作。

目标是让用户不离开事件工作台即可完成 80% 的处置动作。

### 6.4 统一状态与任务语言

内部各模块可保留精确状态，但面向用户统一为七个阶段：

`待研判 → 待核实 → 待处置 → 待授权/执行 → 待办案 → 已关闭`

每个阶段必须配置：进入条件、责任角色、允许动作、必填材料、完成条件、超时规则和回退规则。

### 6.5 把“建议动作”升级为可执行任务

系统不只显示“建议核实、建议反制”，而是生成任务：

- 任务名称：核实禁飞区闯入；
- 原因：命中禁飞区 + 轨迹稳定 + 来源置信 93%；
- 负责人：当班值班员；
- 时限：5 分钟；
- 操作：确认属实 / 标记误报 / 升级授权；
- 完成后自动：更新事件阶段、写审计、生成证据、通知下一角色。

## 7. 重点页面改造

### 7.1 新建“我的工作台”并设为默认首页

首屏只放四类内容：

1. 需要我处理的任务；
2. 需要我关注的风险；
3. 已超时或被退回的事项；
4. 最近处理和交接记录。

地图和统计作为第二层内容，不再承担所有角色的默认入口。

### 7.2 融合感知：从技术监视页变成事件发现页

- 首屏突出高风险目标、规则命中、异常持续时间和建议动作；
- 融合来源、权重、点型放入“判定依据”；
- 地图点击后直接创建/打开事件，不再仅切换目标；
- 支持“只看需要我处理”“只看未分派”“只看即将超时”。

### 7.3 告警中心：从告警台账变成分诊队列

- 默认按风险 × 时效 × 可信度综合排序；
- 增加责任人、等待时长、SLA、来源可靠性、是否重复告警；
- 支持批量合并、批量分派和快速标误报；
- 右侧详情改为“结论—依据—动作—历史”，并提供“继续处理”主按钮；
- 同一目标的重复告警聚合为一个事件，避免 635 条列表造成认知负担。

### 7.4 反制授权：改成分步式安全操作

- 第一步：目标与违规事实；
- 第二步：合法目标、地面风险和空域冲突；
- 第三步：设备、方式和参数；
- 第四步：双确认与下发。

每一步都显示“通过/阻断/需人工判断”，阻断项固定在顶部。最终下发前展示一页简短摘要，减少长弹窗滚动造成的遗漏。

### 7.5 处置与处罚：改成案件办理台

- 左侧不是普通列表，而是“待补证、待审核、待通知、待复核”的任务队列；
- 右侧固定展示当前环节、缺失材料、下一步和责任人；
- 文书生成、通知回执、复核意见、证据补齐都在案件内完成；
- 告警转案件时自动携带目标、判定、轨迹、视频和处置记录，避免重复录入。

### 7.6 证据管理：一套底座、两个入口

- 办案入口：按案件展示证据清单、缺口、冻结和可用性；
- 档案入口：按文件展示完整性、留存、引用和销毁审批；
- 所有查看、下载、校验、补传、销毁都形成审计事件；
- 真实文件服务需支持授权下载、断点续传、水印、哈希复核和到期任务。

### 7.7 设备管理：异常自动转工单

- 异常/离线触发工单，自动关联受影响区域、感知能力和正在执行的处置任务；
- 工单包含负责人、优先级、时限、诊断记录、备件、恢复验证；
- 设备详情、实时监测和调测在同一设备工作台内以标签页呈现；
- 设备恢复后必须经过平台侧指标验证，才能关闭工单。

## 8. 技术改造方案

### 8.1 原则：保留规则资产，替换运行底座

现有 `mock.js` 中的领域规则、枚举、推导和断言是重要资产，不应在 UI 重构时丢失。建议拆成四层：

1. **领域层**：目标、事件、任务、案件、授权、证据、设备、飞行计划的实体和状态机；
2. **应用层**：核实、分派、授权、处置、补证、办结等用例；
3. **适配层**：MockAdapter、HttpAdapter、WebSocketAdapter、FileAdapter；
4. **界面层**：Vue 页面和组件，只消费应用层，不直接访问 `window.MOCK`。

### 8.2 先建立统一事件与任务模型

建议核心主键关系：

`Event → Target[] / Alarm[] / Task[] / Case? / Authorization[] / Evidence[] / DeviceImpact[]`

所有页面通过事件 ID 进入同一上下文，其他编号作为业务附件，不再成为导航负担。

### 8.3 建立真实流程服务

- 工作流/状态机服务：阶段、条件、权限、回退、超时；
- 任务服务：创建、领取、转派、协办、催办、交接；
- 通知服务：站内、短信/政务消息、外部回执；
- 审计服务：人、时间、终端、前后值、理由、结果；
- 文件证据服务：上传、下载、哈希、冻结、留存、销毁；
- 实时数据服务：WebSocket/SSE 接收目标、轨迹、设备和处置回执。

### 8.4 权限从“矩阵展示”变成全链路门禁

- 路由可见性；
- 页面数据范围；
- 操作按钮；
- API 权限；
- 敏感字段脱敏；
- 下载、授权、规则修改二次确认；
- 所有权限变更双人复核与审计。

前端权限只负责体验，最终授权必须由后端再次校验。

### 8.5 渐进式去 legacy

当前约 2.3 万行 JS/Vue，仍同时保留 legacy 脚本和 Vue 页面，且大量依赖 `window.*`、`innerHTML` 和命令式事件委托。建议按用户价值而不是按页面数量迁移：

1. 先新建 Vue 原生工作台和统一事件工作台；
2. 将告警、案件、证据、设备工作台迁为 Vue 原生组件；
3. 抽取表格、筛选、详情头、时间线、任务卡、证据卡等组件；
4. 把领域规则从 `mock.js` 拆出为可测试模块；
5. 最后下线 legacy host 和重复页面脚本。

### 8.6 测试体系补齐

保留现有数据断言和注入证伪，并新增：

- 领域状态机单元测试；
- API 合同测试；
- 权限矩阵测试；
- 核心流程端到端测试；
- WebSocket 断线、重连、乱序和重复消息测试；
- 文件证据完整性测试；
- 可访问性自动扫描与键盘回归；
- 1280、1440、1920 和 200% 缩放视觉回归。

## 9. 90 天实施路线

### 阶段 A：0–2 周，业务定标

- 跟岗观察五类角色各 2–3 人，记录真实一天的任务、表单、电话、微信群和线下交接；
- 选定三条 P0 流程：告警处置、案件办理、设备异常；
- 统一事件、状态、角色、时限和完成条件；
- 建立现状基线：响应时间、页面跳转、线下流转、证据缺失、超时率。

输出：岗位任务地图、事件模型、状态字典、P0 原型范围、指标基线。

### 阶段 B：3–6 周，先解决“会不会用”

- 上线角色化“我的工作台”；
- 上线统一事件工作台前端原型；
- 告警队列增加责任人、SLA、下一动作；
- 状态和编号在页面层统一；
- 反制授权改为分步流程；
- 完成第一轮一线用户可用性测试。

这阶段可继续使用现有 MockAdapter，快速验证产品组织方式。

### 阶段 C：7–12 周，解决“能不能真用”

- 接入真实身份、RBAC、任务、流程、通知、审计和文件服务；
- 打通告警 → 处置 → 案件 → 证据闭环；
- 打通设备异常 → 工单 → 恢复验证闭环；
- 建立 WebSocket 实时数据和外部系统回执；
- 对三条 P0 流程进行灰度试运行和数据复盘。

### 阶段 D：12 周以后，规模化

- 飞行计划预审与风险任务化；
- 领导驾驶舱从“展示指标”改为“闭环成效和督办”；
- 报告模板、跨部门协同、移动端/大屏适配；
- 完成 legacy 退场和统一组件库。

## 10. 优先级清单

### P0：不做就难以成为生产应用

1. 角色化工作台与真实登录；
2. 统一事件工作台；
3. 任务、责任人、SLA、转派和交接；
4. 告警—处置—案件—证据状态机；
5. 真实持久化、审计、文件和外部回执；
6. 后端 RBAC 和敏感操作门禁；
7. 设备异常工单闭环。

### P1：显著提升效率和管理价值

1. 重复告警聚合与智能排序；
2. 计划执行异常自动任务化；
3. 案件缺证检查与自动组卷；
4. 跨部门通知、催办与回执；
5. 领导督办与事件复盘；
6. 键盘、字号、对比度和缩放优化。

### P2：在主链路稳定后增强

1. 个性化布局和常用筛选；
2. 移动值守与现场处置；
3. 预测性设备维护；
4. 智能摘要和辅助研判，但保留人工确认与证据出处。

## 11. 成功指标建议

以下目标应在跟岗调研后签认：

- 事件全流程线上闭环率 ≥ 80%；
- 高风险告警首次响应时间下降 ≥ 50%；
- 完成一件事件的跨页面跳转中位数 ≤ 3 次；
- 证据完整率 ≥ 95%；
- 处置任务超时率下降 ≥ 40%；
- 异常设备平均恢复时间下降 ≥ 30%；
- 一线目标用户周活跃率 ≥ 70%；
- 线下表格、微信群和电话转派数量下降 ≥ 50%。

## 12. 建议立项方式

不建议以“页面美化”或“二期功能补充”名义立项。建议项目名称和验收方式都围绕业务结果：

**立项主题：低空安全事件闭环与岗位工作台改造。**

首期只承诺三条闭环：

1. 高风险告警从发现到处置完成；
2. 违法事件从人工核实到处置与证据留存；
3. 异常设备从告警到恢复验收。

验收不再以页面数量为主，而以真实用户能否独立完成、数据是否留痕、任务是否按时闭环为准。
