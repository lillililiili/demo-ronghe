# 无人机融合感知平台：事件驱动业务流程梳理

## 1. 核心判断

当前系统已经有目标、告警、案件、授权、证据、飞行计划、设备和角色权限等领域对象，但缺少一个真正作为业务主线的 `Event（事件）` 聚合根。

应明确以下区别：

- **感知目标**：雷达、光电、Remote ID、TDOA 等系统持续跟踪的客观对象。
- **告警**：规则或设备产生的一次技术信号；同一目标可以产生多条告警。
- **事件**：需要人负责、需要按时闭环的一件业务事项；一个事件可以聚合多个目标和告警。
- **任务**：事件当前阶段分配给某个岗位或具体人员的可执行动作，必须有责任人、SLA、完成条件和结果。
- **授权**：反制、干扰等高风险动作的安全门禁，不是每个事件都必须经过的阶段。
- **案件**：事实清楚、主体可认定、证据达到要求后产生的执法子流程，不等于事件本身。
- **证据**：从发现开始持续形成的跨流程记录，不是最后一步才生成的材料。

建议关系：

`Event → Target[] / Alarm[] / Task[] / Authorization[] / Case? / Evidence[] / ExternalReceipt[]`

## 2. 当前流程的主要问题

### 2.1 缺少统一事件主键

当前用户沿着目标编号、告警编号、案件编号、授权编号和证据编号跨页面查找。数据之间虽然有关联，但页面没有用一个事件编号承载完整上下文。

### 2.2 把三类流程错误地串成一条直线

当前六环节为：

`告警触发 → 人工核实 → 立案 → 反制处置 → 信号干扰 → 结案归档`

这里混合了三类不同流程：

1. 实时安全处置：发现、核实、风险控制、结果确认；
2. 高风险授权：安全校验、审批、执行、回执、急停；
3. 行政办案：立案、调查取证、审核、处罚、送达、归档。

它们应当按条件并行或衔接，不能要求每个事件顺序走完。

### 2.3 人工核实分支过少

当前只有“属实”和“误报”。实际至少需要：

- 违法属实；
- 合法飞行或已授权；
- 误报；
- 信息不足，继续跟踪或补充证据；
- 需要跨部门协查；
- 非无人机目标，转空间安全事件。

“属实”也不应直接等于“反制中”，需要根据风险等级、所在空域、目标行为和处置条件选择警告、联系飞手、持续监视或申请反制。

### 2.4 反制方式被当成固定阶段

“信号干扰”应是反制方式之一，而不是反制后的固定下一环。返航、迫降、诱骗、导航压制、通信干扰等方式应由授权任务选择，并记录设备、参数、影响评估、审批人、操作人、结果和急停记录。

### 2.5 事件状态与子对象状态不一致

告警、案件和风险事件各自有一套状态，同一件事可能同时出现“已确认、待核实、处置中、待通知”等不同词。应保留子对象精确状态，但对用户提供统一事件阶段。

### 2.6 有岗位权限，没有可交接的任务

系统已定义值班员、处置授权人、设备运维、审计员等角色，但事件缺少具体责任人、领取、转派、协办、催办、SLA、阻断原因和交接记录。

### 2.7 证据和关闭条件放得太晚

证据应从首次探测、规则判定、人工核实、授权、设备指令到外部回执持续形成。事件关闭必须有明确条件，不能因为单个告警“已关闭”就视为整件事完成。

## 3. 通用事件生命周期

所有事件模板共用一个骨架：

`触发 → 聚合去重 → 自动研判 → 分级分派 → 人工核实 → 路由处置 → 结果确认 → 复盘关闭`

统一对外阶段建议为：

`待分诊 → 待核实 → 处理中 → 待结果确认 → 后续办理中 → 已关闭`

辅助状态为：

`已挂起 / 已升级 / 已转派 / 协办中 / 已重开`

每个阶段必须配置：责任岗位、可执行动作、必填材料、SLA、完成条件、回退条件和超时升级规则。

## 4. 黑飞事件完整流程

### 4.1 触发与聚合

1. 雷达、光电、Remote ID、TDOA、5G-A 等产生目标或告警。
2. 系统按目标身份、时空邻近、航迹连续性和规则命中进行聚合去重。
3. 创建或更新唯一事件 `EVT...`，多个重复告警挂在同一事件下。

### 4.2 自动研判

系统完成目标融合、身份识别、飞行计划匹配、空域规则判断、风险评分和证据充分性检查，并输出：

- 当前结论；
- 结论依据和不确定项；
- 风险等级；
- 推荐动作；
- 首次响应 SLA。

### 4.3 值班员核实

事件自动分派或由值班员领取。值班员查看轨迹、视频、计划、空域和历史告警后选择：

- 误报：记录原因并关闭；
- 合法飞行：修正匹配关系并关闭；
- 信息不足：继续跟踪、补证或发起协查；
- 非无人机目标：转换为空间安全事件；
- 违法属实：进入风险控制。

### 4.4 风险控制

- 低/中风险：联系飞手或所属单位、警告纠正、持续监视；
- 高/重大风险：创建反制授权任务；
- 目标已离场但违法事实成立：实时风险解除，转后续调查或案件办理。

### 4.5 授权与反制（条件分支）

处置授权人检查目标、合法目标影响、地面风险、空域冲突、设备状态和操作参数，选择批准、驳回或调整方案。

批准后由操作人员执行选定方式，系统记录指令、设备回执、操作人、审批人、时间、参数、结果和急停过程。执行失败时应升级、切换设备或调整方式，不能直接推进到下一阶段。

### 4.6 结果确认

确认目标返航、迫降、离场、被控制或风险已解除。实时处置完成时间与行政办案完成时间分别统计。

### 4.7 案件办理（条件分支）

满足事实清楚、主体可认定、证据充分、管辖明确等条件时创建案件；否则生成调查、主体认定或补证任务，不能从流程中静默消失。

案件子流程：

`待立案 → 调查取证 → 审核/审批 → 处罚决定 → 通知送达 → 复核/申诉 → 归档`

### 4.8 事件关闭

只有同时满足以下条件才允许关闭事件：

- 实时安全风险已经解除；
- 必做任务已完成或已正式移交；
- 授权和设备执行结果有回执；
- 证据包完整性校验通过；
- 外部通知有回执或已形成超时处置记录；
- 案件已完成，或明确记录为不立案/移交并说明依据；
- 责任人完成结案说明和复盘。

## 5. 建议支持的事件流程

### 5.1 非法/身份异常无人机事件（P0）

未经批准、禁飞区闯入、身份不匹配、超视距、夜间飞行等。核心是核实、实时风险控制、条件授权和条件立案。

### 5.2 报备飞行异常事件（P0）

偏航、超高、超时、计划未匹配、计划与实际身份不一致。先联系责任主体并要求纠正；持续或严重违规时升级/转换为非法飞行事件，保留原事件链路。

### 5.3 非无人机低空安全事件（P1）

鸟群、气球、孔明灯、风筝及其他未知物。以识别、影响评估、通知避让、驱离或持续监视为主，默认不进入行政处罚；识别为无人机后可转换事件类型。

### 5.4 设备异常与能力中断事件（P0）

设备离线、性能异常、数据中断、反制设备不可用。自动生成工单，评估受影响区域和正在进行的事件，分派运维，诊断维修并由平台侧恢复验证后关闭。

### 5.5 证据与合规异常事件（P1）

哈希不一致、文件缺失、待校验、留存到期、冻结冲突或异常访问。先锁定材料，再调查、恢复、补证、审批和复核；异常未解决时阻止相关案件关闭。

### 5.6 外部指令与跨部门协同事件（P1）

上级指令、公安协查、跨区移交、通知回执超时。必须有接收确认、责任分派、处理反馈、重试/催办和最终回执。通常作为安全事件的协同子流程，也可以独立存在。

### 5.7 数据质量与规则异常事件（P2）

融合结果冲突、置信度异常、误报率激增、设备数据互相矛盾。分派给算法或数据治理人员，完成样本复核、规则调整、版本审批、灰度验证和回滚。

## 6. 首期建议

首期不要同时建设所有模板，优先做三条能证明事件驱动价值的闭环：

1. 黑飞事件：发现到实时处置，再到条件立案和证据归档；
2. 报备飞行异常：偏离发现、责任主体通知、纠正或升级；
3. 设备异常：告警、工单、维修、恢复验证。

工作台、事件中心和所有详情页都围绕事件 ID、当前责任人、SLA、下一动作、阻断原因和统一时间线组织。
