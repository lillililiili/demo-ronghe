## 数字怎么来的

全部数字来自四个库的 `flyway_schema_history` **现查**，不是从简报或计划里抄的：

```sql
select case when version is null then '可重复' else '版本化' end, count(*)
  from flyway_schema_history where success group by 1;
select count(*) from flyway_schema_history where not success;
select min(installed_on), max(installed_on) from flyway_schema_history;
```

| 库 | 总记录 | 版本化 | 可重复 | 失败 | 首次 / 最近 |
| --- | --- | --- | --- | --- | --- |
| `uav_stage15_fresh` | 70 | 61 | 9 | 0 | 2026-09-08 / 2026-09-08 21:59 |
| `uav_stage16_fresh` | 70 | 61 | 9 | 0 | 2026-09-09 / 2026-09-09 02:49 |
| `uav_stage16_upgrade` | 70 | 61 | 9 | 0 | 2026-09-09 / 2026-09-09 02:40 |
| `uav_stage10_verify` | 72 | 61 | 11 | 0 | 2026-09-07 / 2026-09-08 07:53 |

**这里我先写错过一次，记下来**：初稿把那条 `type=JDBC` 的记录当成了 Flyway 基线行，于是写成"61 + 9 + 基线 1"，加起来是 71，与实际的 70 对不上。实查后确认它是**用 Java 写的版本化迁移**（版本号 `202609070104`，内容是设备类型缩写），本身就在 61 里，没有额外的基线行。正文已改为"61 + 9 = 70"。**数字相加对不上是最容易被验收方一眼看出来的错**，交付前逐个加过一遍。

**72 与 70 的差额已查明**：`uav_stage10_verify` 上 `R__stage13 disposal` 一条脚本先后执行过 **3 次**（`select description, count(*) ... group by 1 having count(*)>1`），其余可重复脚本各 1 次。所以差额来自可重复脚本的重复执行，**不是版本化迁移的分叉**——两边都是 61。正文把这一点单独写出来，因为"升级库比新装库多两条记录"如果不解释，验收方第一反应会是"结构不一致"。

## 写作时做过的判断

1. **正文以"结构性变更 61 步两边一致"开头。** 这是整份文档里唯一一句能直接回答"升上来的库和新装的库一不一样"的话，放在最前面；其余都是支撑。
2. **专用升级夹具那一节写明"证据是分开取得的、不是成对实验"。** 负例（新版本没做错）是实测的，正例（旧版本会做错）来自另一个库上更早的运行记录，且那个有问题的程序包已不可得。**不写这句，读者会默认那是一次对照实验**；写了，将来复查的人才知道该补什么。
3. **"未运行"与"通过"在自动化检查表里分开标。** 前两次的界面走查是没跑，不是跑过没问题——这两者在结论栏里如果都写成空白或"—"，会被读成"没问题"。
4. **第五节把没有的东西列清楚**：具体命令行与耗时无留存、更早阶段无记录、生产环境尚未进行。**生产尚未进行这一条尤其要写**，否则一份叫《安装与升级记录》的文档会被默认为包含生产。
