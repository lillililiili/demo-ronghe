# 合法性判定与告警模块分工评审

日期：2026-09-22。状态：基于现有代码的设计建议，未修改业务代码或启用规则。

分析依据：本轮 Excel 的44种场景、用户后续确认的“业务归属与操作入口分开”、两级项目约定、前端及同级后台代码。检查时磁盘上的工作簿仍为“主要处理页面”列，本评审以对话中后来确认的模块边界为准，不覆盖工作簿。

## 1. 定位与推荐方案

保留飞行计划／合法性判定和告警／处置两个模块。前者拥有计划比对、合法性研判及复核；后者拥有风险事件、通知、设备反制与响应记录。已有关联告警时，在告警详情原地打开同一份研判复核，不让操作员来回跳页。

| 方案 | 收益 | 代价 | 结论 |
|---|---|---|---|
| 两个模块，共用研判与复核，在告警原地操作 | 分工明确，风险响应不中断 | 需打通关联、结果传播和动作校验 | 推荐 |
| 两个模块，只互相跳转 | 前端改动较少 | 重复核实、状态分裂仍存在，值班员来回操作 | 仅适合临时过渡 |
| 合并全部页面和流程 | 少一个导航入口 | 计划、研判、事件、设备授权混杂，扩大现有需求 | 不采用 |

本文件中的 L/A/P 编号仅用于评审定位，不是新增业务编号。

## 2. 上下游与生命周期

有效目标观测、计划及规则进入合法性研判；命中有效风险触发条件时生成或更新告警。研判可靠性决定是否需要人工复核，通知及反制资格各自独立检查。恢复观察、事件处理和事后移送分别保存事实。

| 来源模块／事件 | 输入 | 处理及输出 | 消费模块 |
|---|---|---|---|
| P1 计划资料、监测观测、后台规则 | 目标、计划、时间、轨迹、适用规则 | 后端计算研判、逐项依据和可靠性 | L2研判详情、A2风险与依据 |
| 后端风险触发 | 有效风险事实、目标、时间、规则 | 按既有去重范围建告警或追加关联 | A1告警列表、A2详情 |
| L3或A2内嵌复核 | 同一研判及版本、结论、说明 | 保存复核并重新评价关联影响 | L1/L2、A1/A2、A3通知、A4反制资格 |
| 通知通道、设备 | 发送、送达、接通、播放、执行回执 | 保存独立事实 | A3/A4；不替代风险解除 |

自动动作不依赖页面停留。新观测、规则生效及复核生效触发后端处理；页面加载和轮询只读。

## 4. 逐模块处理规则

| 模块 | 出现条件与输入 | 展示／计算与人工动作 | 写入、生效与下游 | 核心验收 |
|---|---|---|---|---|
| P1 | 有权限访问的关联计划 | 计划时段、航线、身份等实际已有资料；缺项如实显示 | 计划修改按现有流程生效，后端基于有效版本重判；不覆盖旧研判 | 旧研判仍能追溯当时计划 |
| L1 | 明确识别为UAV | 保留待处理默认范围；区域、计划、判定、复核和核实位置筛选 | 查询不写状态；统计、列表、分页使用同范围 | 非UAV和未知类别不能混入 |
| L2 | 精确选中的研判 | 原系统结论、有效复核结论分开；判定及观测时间分开；按实际点画轨迹 | 提供决策信息和精确关联导航，不自行计算合法性 | 不能用另一目标或另一事件的最新记录替代 |
| L3 | 后端判定需复核且具备权限；可靠结论允许按现有入口纠错 | 共用确认、驳回、改判和说明；重算生成新研判 | 使用原研判ID、版本与幂等键；保留历史；后端评价关联影响 | 两入口只能产生一份有效提交，冲突先回读 |
| A1 | 有权限的风险事件 | 显示事件风险与响应摘要，不以短信资格覆盖核实结论 | 点击只传递当前事件；处理后刷新同源统计 | 不能按44个Excel条目新增44个告警类型 |
| A2 | 当前事件及其有效关联依据 | 第一屏显示当前风险、判定依据、时间与自动动作；仅需人时显示核对入口，原地复用L3 | 研判修改归L3；独立事件争议按原事件流程处理，不混成同一结论 | 同一研判不再要求重复确认；独立争议仍保留 |
| A3 | 当前事件的真实通知任务与回执 | 两渠道独立展示；详情收纳接收人、时间与失败原因 | 触发或重试由后端策略、权限及时效校验 | 一个渠道成功不能覆盖另一个；未接通不造成功 |
| A4 | 当前事件、授权、有效观测、充分违规依据和设备状态 | 保留人工发起、申请／直接反制、审批、执行监测、急停及历史 | 每次提交、排队下发、续链检查当前条件，按设备回执展示 | 原地复核不授予反制权限、不自动执行 |
| A5 | 后端自动移送状态或既有交接 | 只读进度和同一交接入口；未启用、失败、未知分别显示 | 后端按实际能力处理，页面不触发移送写入 | 查看不创建交接，历史冻结材料不回写 |

各模块不新增生成式AI；当前规则计算和证据充分性不能宣称统计准确率已验证。除有独立意义的事件争议外，可靠明确结论不加人工确认关卡。

## 9. 状态设计

继续区分四组状态，不新增一个总状态包办全部事实：

1. 研判结果：合法、异常、非法、不可判定；不适用／过期保留原因。
2. 复核进度：待复核、已确认、已驳回、已改判、被重算取代。
3. 告警事实：待核实、告警已确认、误报等现有后端状态。
4. 响应进度：通知各渠道、反制授权与执行、移送分别记录。

建议转换原则：可靠违规依据可由后端策略采纳为事件依据；不要求操作员为同一事实重复填写“属实”。不确定项完成一次复核后，后端重新检查当前事件的全部依据与独立争议，再决定是否结束对应待办。改判合法或驳回单份研判不自动关闭全部关联告警。仍有其他有效风险时继续响应；无足够证据时标为待核对／未知，不冒充恢复。

这是待实现的后端流程变化。不得直接删除现有CONFIRMED校验，或在前端把事件一律改成CONFIRMED。

## 10. 自动判定与人工介入

| 场景 | 自动动作 | 人工介入 | 失败后 |
|---|---|---|---|
| 可靠明确结论 | 采纳结论，按独立规则触发风险及通知 | 仅发现新证据或实际异常时纠正 | 不依赖页面进行处理 |
| 必要依据不足 | 继续有效数据比对，呈现具体缺口 | 核对同一份研判 | 未补足仍不可判定 |
| 已有可信风险、其他检查未知 | 已有风险继续响应 | 核对未知部分 | 未知不能覆盖已证实风险 |
| 数据过期、目标失联 | 保留最后观测及历史通知，明确当前未知 | 处理数据异常 | 不当作飞离，不允许依赖过期依据下发反制 |

对“计划匹配不确定，但有独立可信禁飞区事实”的告警触发，现有引擎可能被综合不可判定结果阻断。应按逐项风险事实及其可靠性明确触发策略，不能简单把所有不可判定都变成告警。该调整属于规则设计和后端实现，须单独验收。

## 11. 权限与范围

| 能力 | 原权限原则 | 设计要求 |
|---|---|---|
| 查看告警 | 告警读取及记录范围 | 不隐含研判修改权限 |
| 从告警复核研判 | 研判读取、复核权限及记录范围 | 同一表单不绕过原权限；无权限只读并说明 |
| 独立事件核实 | 原告警核实权限 | 只处理独立事件争议 |
| 设备反制 | 直接反制、申请、审批、设备权限分别校验 | 保留主体、组织范围、时效、急停与审计要求 |

关联ID被权限隐藏不能冒充未生成告警。历史、材料和视频继续按各自权限读取。实际角色组合沿用后台配置，不发明新岗位或默认授予权限。

## 12. 异常与恢复

| 情况 | 界面及系统处理 |
|---|---|
| 首次加载／空记录 | 明确加载或无记录；不显示虚构正常结论 |
| 部分关联缺失 | 已知事实继续显示；准确指出缺少哪份关联 |
| 无权限 | 只读可见内容；不借另一页面权限提交 |
| 告警生成BLOCKED | 显示生成受阻原因；没有实际告警不能误导到不可用入口 |
| 当前记录被新研判取代 | 保留历史，定位明确取代关系；不能按目标随意选最新记录 |
| 两人并发提交 | 乐观版本与幂等键校验，回读当前状态，不生成重复历史 |
| 提交超时／断网 | 结果未知，先回读，不宣称成功，不换键盲重试 |
| 复核已保存但关联处理失败 | 分开展示保存结果和关联失败；后端可恢复，前端不伪装同步成功 |
| 设备受阻／回执未知 | 保留真实状态，不转为人工执行或手填成功 |
| 已由他人处理 | 回读共享结果并刷新两页队列；不重复要求填写 |

| 前台 `LegalityPage.vue` | alarm_outcome_kind非SHADOW即可视为告警办理；包括可能无告警的BLOCKED | 使用后端真实关联事实，区分无告警、生成失败与权限受限 |
| 后台 `AlarmMergePolicy.autoCloseExpired` | 自动关闭的是合并组，不是告警事件 | 不把合并组到期等同风险解除 |

复用现有 `/legality-evaluations/{id}/revisions` 复核命令；不新造第二套告警合法性复核接口。新增的是事件到研判的精确读取／采用结果契约和后端处理语义，具体扩展字段尚未实施。后台管理端和业务前台两消费者同步检查。历史事件事实、原始研判及冻结交接不回填成新流程结果。

## 14. 端到端验收

1. 有效正常飞行：合法性页显示结论，无新风险告警，无强制人工确认。
2. 仅计划服务失败：显示依据不可用，不认定黑飞；无告警时合法性页核对。
3. 有效偏航：研判形成依据并触发已配置告警；通知按两渠道记录；不自动反制。
4. 有告警且需复核：告警内原地提交一次，合法性页看到同一版本和历史；刷新、重新登录仍一致。
5. 可靠违规：无需重复填写同一事实；反制仍需人工发起并满足全部后端条件。
6. 复核完成但仍不可判定：复核状态更新，信息缺口保留，待处理并集统计正确。
7. 同一事件有多条风险依据：驳回一条不消除其他有效风险，不自动关闭整个事件。
8. 目标失联：保留历史送达与执行事实，当前状态未知，失效依据不能继续用于反制。
9. 告警生成受阻和关联被权限隐藏分别展示；既不误导空跳转，也不绕过权限。
10. 无研判关联的旧事件和独立争议仍有可用办理路径，不批量改成已核实。
11. 两入口同时提交或超时重试只有一次生效；关联传播失败可恢复并可追溯。
12. 列表、详情、分页、统计、待办及反制资格采用一致事实；真实通道与设备另行验收。

## 15. 尚需确定的规则

| 项目 | 已确定部分 | 待确定边界 |
|---|---|---|
| 模块与入口 | 两模块保留；告警优先原地核对同一研判 | 共用入口的具体布局可按当前页面局部实现 |
| 无计划／疑似黑飞 | 资料缺失不能直接认定无授权 | 何种完整证据及持续条件触发待核实风险 |
| 独立可信风险加其他未知 | 不能掩盖已证实风险 | 按项触发策略与综合结论的关系及适用配置 |
| 复核结果采用 | 共享研判、保留原始结论和历史 | 哪些有效依据可解除事件对应待办；独立争议如何识别 |
| 风险解除 | 需要有效观测和规则依据 | 各类恢复阈值、持续时间；不能以合并组到期代替 |

不新增黑名单、危险载荷识别等未经确认的能力，不把44条清单逐条映射为新告警类型。技术失败、办理后续和真实飞行违规是不同性质的条目。

## 16. 实施顺序与评审结论

推荐先明确当前采用依据及关联关系，再实现后端一次复核的结果传播和反制资格回读；随后让告警详情内嵌同一复核表单，配套两页队列与统计；最后核对每类风险触发、通知、恢复规则和真实接入。

当前已具备计划、研判、告警、通知、反制等基础能力。缺口集中在同一研判复核的结果消费、重复事件核实的分流、误关联／受阻入口以及风险触发与解除边界。页面合并无法解决这些问题。
