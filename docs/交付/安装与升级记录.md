| | 空库安装 | 旧库升级 |

| 结构性变更（一次性执行、按顺序编号） | **61 步** | **61 步** |
| 校验类脚本（每次升级都重新执行一遍） | 9 条 | 11 条记录 |

结构性变更两边都是 61 步、完全一致——**这是"升级上来的库和新装的库能力相同"的直接证据**。

| 核对结果 | 升级后服务正常启动；历史数据保留；结构性变更步数与新装库一致 |

### 升级路径上真正暴露出来的问题

**这条路径的价值在于：有几类问题只有在"已经装过、有历史数据"的库上才会现形，新装的库看不见。** 本项目在升级验收中实际遇到并已修复的有：

1. **一次"净效果为零"的升级**：某一步变更把一批权限等级归一到正确值，但同一次启动中随后运行的自检程序又把它们改了回去。由于该变更已被记为"已执行"、不会再跑第二遍，如果只看新装的库，这个问题完全看不出来。修法是先修正自检程序，再补一步新的变更重新归一——**而不是修改那一步已经执行过的变更**。
2. **陈旧目标被错误合并**：升级上来的库里存在长期存在、但本轮完全没有被观测到的历史目标，自动合并把它们当成了候选，产生了一条不该有的合并链。新装的库里没有这类历史目标，因此同样看不见。
3. **一份已经执行过的变更被修改**：修改后其校验值改变，导致所有已经执行过它的库在下次启动时直接停在校验不通过上。已确立规则：**已执行过的变更一律不改，要改就新增一步**。

### 升级路径的核对项

1. 结构性变更步数与新装库一致（61 = 61）；
2. 无失败的变更记录；
3. 历史业务数据仍在、且可以正常打开；
4. 升级后新增能力可用；
5. 自检程序重复运行不会破坏已归一的数据。

## 三、专用升级夹具

代表环境：`uav_stage16_upgrade`（2026-09-09 建立）。

这是为验证"自动合并不会误并历史目标"专门准备的库：**先用旧版本程序灌入一批数据造出历史状态，再用新版本程序启动**，以此检验新版本在有历史包袱的库上的行为。

| 项目 | 记录 |
| --- | --- |
| 数据库变更 | 70 条记录，结构性变更 61 步，失败 0 |
| 灌入数据 | 回放消息 204 条、观测 237 条、目标 31 个 |
| 检验结果 | 新版本启动后：自动合并只发生 1 次（正确的那次），未产生错误的合并链；一个位于合并判定范围之内、但本轮没有被观测到的历史目标**被正确地放过了** |

**这一条的证据完整性需要说明**：上述是"负例"——新版本没有做错事。与之对应的"正例"（旧版本确实会做错事）来自另一个库上更早的一次运行记录，**两者不是在同一个库上做的成对实验**，且当时那个有问题的程序包已经不可得。因此这条结论的证据是**分开取得的**，而不是一次严格对照实验。
