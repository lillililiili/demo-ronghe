# 告警到处置三期开发与 MQTT 闭环验收计划

编制日期：2026-09-18。状态：待实施的整体计划；不代表所列功能已上线。

## 1. 目标、范围与完成定义

以现有业务前台 `dongying-vue`、管理端 `../houtaiguanli/ruoyi-ui`、唯一后端 `../houtaiguanli/server` 为基础，分三期完成：

1. 自动研判闭环：可信事实自动判断，证据不足转人工，通知与现场观察按条件推进。
2. 辅助反制与执行闭环：系统整理依据和建议，人工作出关键授权，系统跟踪指令、回执和现场效果。
3. 受控自动执行与移送：明确有效的预授权范围内自动推进，自动移送、签收跟踪和补充材料形成事后闭环。

最终使用 MQTT 连续模拟输入，经真实后端业务处理，完成同一目标、同一事件的全过程验收。通过标准不是各页都有演示数据，而是能从一条原始消息追到研判、事件、通知、观察、授权、指令、回执、效果结论、交接及其材料和签收结果。

闭环分为两条相互关联的业务线：

| 业务线 | 结束依据 | 不可替代的事实 |
| --- | --- | --- |
| 实时处置 | 有效观测证明风险解除；或明确进入有责任人、原因和后续要求的异常接管状态 | 短信送达、指令成功、观测中断、材料移送均不等于风险解除；异常接管也不等于处置成功 |
| 事后移送 | 材料已移送、接收方已签收，能够关联办理进度或明确等待结果 | 已发送不等于签收，签收不等于处罚决定或案件办结 |

不要求每个告警都执行反制。合法、误报、通知后自行飞离、反制后解除、失联转人工等分支均属于验收范围。是否移送由独立策略决定，不能把“反制完成”设为所有移送的前提。

本轮交付开发计划，不执行数据追加、服务配置修改、真实通知或设备动作。第三期预授权是拟新增能力，当前人工发起反制的规则保持有效，直到该能力完成授权配置和验收。真实通道、真实设备和生产启用分别验收，不由 MQTT 模拟验收替代。

## 3. 三期共用设计

### 3.1 事实、判断、授权和动作分开

保留事件原有核实历史，新增或扩展独立判断结果：来源为系统研判或人工复核，保存输入引用、结论、充分性、未知原因、规则/算法版本、生效时间和失效时间。系统判断不能伪造人工 `CONFIRMED` 记录。

统一各动作的资格判定入口，返回是否允许、依据引用、阻断原因及下一步处理要求。通知、反制建议、反制执行、移送使用各自资格，不用一个“已核实”覆盖全部条件。反制仍额外核对有效授权、目标和设备范围。

### 3.2 后台持续推进

复用现有任务、指令、通知、授权和交接模型，增补必要持久状态，不另建与它们竞争的整套状态机。观测/判断/回执更新驱动重新评估，后台调度负责超时和漏处理补偿。

动作任务至少具备稳定幂等键、条件版本、关联对象、领取租约、尝试次数、下次检查时间、当前状态、失败原因和审计。数据库事务内保存业务变化与待办任务，外部调用在短事务之外执行。

重复消息、并发调度、重启与迟到回执不能导致重复通知、重复授权、重复受控指令或重复移送。结果未知先对账，不能因超时盲目重发；无法自动核清时转人工。关闭网页、注销用户不影响系统任务；用户撤权、授权过期仍必须阻断新执行。

### 3.3 多维进度与统一查询

事件概览由后端汇总，至少区分：事实结论、通知渠道结果、当前观察与风险、授权、执行、移送、异常处理。列表、详情、统计和其他页面使用同源事实与统计口径。

“已批准待执行”与“执行中”分开；“执行完成”与“风险解除”分开；“已移送”不覆盖现场风险。新鲜度影响当前动作资格，不覆盖既有送达或执行历史。所有关键结论显示依据与更新时间。

### 3.4 参数与追溯

观测时效、连续观察窗口、通知等待、回执超时、重试次数和授权期限集中配置并版本化。实施时根据实际输入频率确定，不沿用文档中的历史数值当正式标准，也不为演示成功临时放宽。

建立 `batch_id / scenario_id → 来源消息 → 目标/轨迹 → 研判 → 告警/事件 → 各渠道任务 → 观察 → 授权/指令 → 效果评估 → 交接/材料 → 签收/案件` 关联清单。可复用既有主键和溯源字段；不强制在每张表重复增加批次列。

## 4. 第一期：自动研判闭环

### 4.1 业务规则

| 项目 | 实施要求 |
| --- | --- |
| 触发数据 | 新目标观测、计划或空域有效版本变化、研判更新、通知回执 |
| 自动依据 | 目标类别、匹配计划、时空关系、合法性结果及证据充分性；识别置信度不替代合法性可靠性 |
| 数据时效 | 校验观测时间、接收时间和研判时间；乱序旧消息不得覆盖新状态 |
| 自动动作 | 自动判定、告警生成/合并、证据引用汇集、允许的飞手提醒与持续观察；各渠道独立推进 |
| 人工介入 | 依据不足、结论冲突、身份不明、无法联系、持续失联或异常处理超过时限 |
| 失败处理 | 保留原因和任务，能够补数据后重新评估；结果未知不显示成功，不自动判合法或飞离 |

### 4.2 开发任务

- P1-01：梳理现有输入/规则版本，确定统一判断结果与动作资格契约；为存量记录保留“旧记录缺少判断依据”，不批量补造结论。
- P1-02：接通系统判断与人工复核分流。明确合法/非法且充分时不要求重复核实；不充分时创建可处理的异常项，保留复核事实与审计。
- P1-03：将自动通知资格接到统一依据，保留短信与电话独立的发送、接通/送达、播放和失败事实；飞手缺失不猜接收人。通知上级继续使用统一目的地，不能替代飞手接收关系。
- P1-04：新增自动现场观察服务。结合相同目标的连续有效轨迹与区域关系，产生仍在区域、确认离开、情况未知等结论及证据引用。丢点、断轨、设备离线和缺少区域依据只能判未知。
- P1-05：新增实时风险结果评估，支持“通知后自行离开”的结束分支；不能将通知成功作为解除依据。观察结论与人工结论冲突时保留双方历史并转人工。
- P1-06：前台接入多维概览，修正“批准即执行中”等错误映射；管理端显示规则配置、判定运行、动作执行状态及阻断原因。
- P1-07：制作合法、明确违规、证据不足、自行离开、失联五类 MQTT 场景，形成阶段验收报告。

### 4.3 阶段出口

新鲜 MQTT 违规输入能够产生可追溯告警并按条件触发模拟通知；可靠判断不依赖人工重复点击；持续有效离开观测能够形成解除依据；失联只能转未知/异常。全过程关闭页面仍运行，刷新和重新登录后状态一致。

本期不启用自动反制；需要反制的事件继续进入第二期人工关键决策流程。

## 5. 第二期：辅助反制与执行闭环

### 5.1 业务规则

| 项目 | 实施要求 |
| --- | --- |
| 触发数据 | 有效违规判断、通知与联系事实、最新观察、人工授权、设备回执 |
| 自动依据 | 当前危险与持续在场事实、既有策略、适用设备能力；建议附带证据，不自行扩大处置范围 |
| 数据时效 | 申请、审批、执行前重新检查；早先的高危险记录不能无限期使用 |
| 自动动作 | 整理反制依据和建议、跟踪已授权任务、关联设备回执、评估执行后的现场效果 |
| 人工介入 | 发起反制、逐次审批或持有效直接权限操作、补充无法自动获得的依据、处置失败及结果未知 |
| 失败处理 | 拒绝/过期不执行；设备失败、超时、停止未确认分别记录；无有效结果不得继续升级动作 |

### 5.2 开发任务

- P2-01：改造反制前置判断，消费第一期可信结果与观察，不再只检查人工 `CONFIRMED`；同时保留独立授权、权限、范围与有效期要求。
- P2-02：生成可解释的反制建议和依据清单。自动观察足够时不重复填表；缺少具体事实时按需补充。保存依据只保存事实，不顺带申请或执行。
- P2-03：复用现有申请、审批、直接反制和设备执行服务；申请、授权、下发、受理和完成独立记录。直接权限不能视作后台无人值守预授权。
- P2-04：完善后台回执收敛，校验来源、设备、目标及指令关联，处理重复、迟到、乱序和重启恢复；停止依赖读详情推进最终状态。
- P2-05：实现执行效果观察窗口。指令成功后继续看目标；仍在场或效果不明保留风险，明确通知人工，不自动生成成功结论或无限重复反制。
- P2-06：核对急停全链，先提交停止再补原因；停止请求与停止回执分别展示。失联或超时显示停止未确认；急停后不自动恢复。
- P2-07：MQTT 模拟器监听本批次设备的真实下发指令，以匹配标识返回模拟成功/失败/无回执/迟到回执；分别验证“执行成功且离开”和“执行成功但仍在场”。

### 5.3 阶段出口

人工授权后，真实后台指令链能够驱动模拟设备回执，并在持续观测下形成效果结论；批准但未下发不能显示执行中，指令成功但目标仍在不能显示解除。错误关联回执不能推进状态。审批、直接操作和急停均有审计。

## 6. 第三期：受控自动执行与移送

### 6.1 业务规则

| 项目 | 实施要求 |
| --- | --- |
| 触发数据 | 第一、二期有效事实、规则命中、有效预授权、移送条件满足、交接回执及新增材料 |
| 自动依据 | 明确动作、目标/范围、设备、有效期限和限制的预授权；移送单独使用可靠违规或人工确认依据 |
| 数据时效 | 每次领取任务、下发、重试/续接前重新检查事实与授权；配置版本变更保留历史 |
| 自动动作 | 授权范围内执行已允许动作；自动创建交接、按策略模拟投递、签收跟踪及补充材料关联 |
| 人工介入 | 创建/批准/撤销预授权，越权或失效处理，急停，接收方配置冲突，送达未知及材料争议 |
| 失败处理 | 越界、过期、失联、撤权、执行失败立即阻断后续自动动作并转异常；已有事实不回滚为未发生 |

### 6.2 开发任务

- P3-01：新增预授权策略及独立管理权限，默认关闭。记录授权人、批准依据、适用对象/区域/设备/动作、起止时间、并发及次数限制、撤销状态和版本；不能用普通规则启用开关代替授权。
- P3-02：将规则命中接入持久化执行任务，复用第二期执行守卫与审计。系统执行主体与授权来源可识别，不借用某个用户登录会话。停用入口阻断后续任务；已经下发的动作按停止与对账流程处理。
- P3-03：开发自动移送任务和 `auto_handoff` 只读概览，保存首次启用时间与适用边界，默认不追溯旧事件。同事件已有交接时沿用，唯一约束和事件锁防重。
- P3-04：定义默认处罚接收方，要求唯一有效配置，缺失或冲突时阻断。统一创建交接与后续通知的资格判定，消除“算法合格可创建但因未人工 CONFIRMED 不能发送”的断点。
- P3-05：复用材料组装和冻结机制，保留提交方式、研判、通知、观察、授权/执行及文件引用。材料缺失清楚列出；后到证据生成补充材料，不回写原快照。
- P3-06：交接创建、发送、送达、签收、办理结果分开。模拟接收适配器提供可信关联回执、失败和超时；查询接口无写入/重发副作用。
- P3-07：保留现有案件结果查询，明确外部结果或现有案件模块的来源。使用模拟办理方经受控接口推进关联案件，或由测试人员通过既有办案接口办理；不由 MQTT 观测直接生成处罚决定。
- P3-08：完成全场景无人值守推进、异常接管、重启和双调度并发验收；发布部署开关、回退与操作说明。

### 6.3 阶段出口

有效预授权场景无需逐次点击即可完成模拟执行，授权不成立时明确阻断；符合移送策略的事件自动生成唯一交接、冻结材料并获得可追溯的模拟签收。前台能关联查询该交接的办理结果，未返回时明确等待。停止发布后任务不会无限运行；重启不会重复外部动作。

## 7. MQTT 模拟与配套工具方案

### 7.1 复用与改造

复用后台现有 `scripts/mqtt_business_test.py`、`mqtt_acceptance_checks.py`、`publish_lingyun_ndjson.py`、`reply_lingyun_control.py` 及实际接入协议。现有控制检查脚本主要证明设备指令协议，不可替代经事件、授权链发起的业务验收。

将现有场景工具扩展为小规模、可选场景的验收运行器，避免默认生成大量无关目标。新增显式输出目录、场景选择、批次、最大时长、消息上限和停止条件；本计划执行时输出到系统临时目录，不沿用现有脚本向仓库 `target` 写验收材料的默认方式。

### 7.2 输入分工

| 输入 | 入口 | 必要限制 |
| --- | --- | --- |
| 设备注册、心跳、观测与轨迹 | 现有 MQTT 协议入口 | 仅本批次设备/主题，沿用消息校验，不伪造实时来源 |
| 设备执行及停止回执 | 模拟器订阅下发指令后返回协议回执 | 匹配实际指令，不预填不存在的授权号，不响应其他设备 |
| 飞行计划、航线、飞手与接收方 | 现有业务 API；必要时受控批次 seed | 先准备关联与有效时段；不得修改旧记录时间 |
| 短信、电话结果 | 独立本地模拟渠道 | 分别模拟发送、送达、接通、播放及失败；不是 MQTT 观测消息 |
| 处罚投递、签收与办理结果 | 独立模拟接收适配器或现有受控 API | 使用同一交接/案件 ID，不能让普通前端填成功回执 |
| 图片、视频、轨迹证据 | 现有文件/证据服务 | 内容实际存在，计算哈希，标记模拟；无录制能力时如实缺失 |

轨迹按合理速度和观测时序生成，保留转弯、停留及中断。符合计划的已飞段绿色、偏离段红色、未飞计划段灰色，未知关系单独显示。模拟设备回执不直接强改目标位置；现场效果通过后续轨迹表达。

### 7.3 运行过程

1. 预检：确认隔离 PostgreSQL/PostGIS、测试 MQTT broker、模拟通道和设备白名单；真实动作与真实通知均未接通。记录代码、迁移、规则、策略和开关版本。
2. 准备：为批次生成稳定对象 ID，准备计划、航线、机构范围、飞手、接收方和必要权限；对拟改记录备份，不触碰其他批次及人工历史。
3. 执行：按场景发布观测，后台自行产生研判和事件。运行器记录派生 ID，按第二期需要等待授权操作或第三期已配置的有效预授权，不绕过守卫。
4. 回执与效果：模拟器匹配实际命令并回执，再按场景发布后续轨迹；通道适配器独立提供对应通知和交接结果。
5. 核验：通过业务 API、只读数据库关系检查和页面检查验证各段；保留原始消息摘要、状态变更时间和失败原因。
6. 停止：达到场景结局、最大时长或失败条件即停止发布并退出本批次应答器。等待在途任务对账，不把停止模拟器解释为目标离开；生成报告，保留历史，不自动删除业务数据。

同批次再次执行以恢复/核验为主，已完成动作不重置；需要重演时使用新批次。同一设备控制流只允许一个应答器，避免现有 stream 与负向测试脚本同时应答。

## 9. 验收证据与质量门槛

- 数据链：消息、目标、事件、任务、授权、指令、交接 ID 正确关联；业务时间先后合理，发送时间与实际回执相符。
- 防重：相同消息、重复请求、重复回执和并发任务不重复产生受控动作；无法保证外部恰好一次时明确依赖渠道幂等与对账，不声称绝对恰好一次。
- 权限：申请/审批/直接执行/预授权管理/停止/结果读取分别验证，跨组织和无权限请求被拒绝；前端隐藏按钮不是验收依据。
- 后台：相关单元与 API 测试，真实 PostgreSQL/PostGIS 迁移、锁、幂等与重启测试；不连接共享业务库运行破坏性测试。
- 前台：受影响工程构建；业务前台执行 `node tools/scan.cjs`、旧管理地址迁移测试；检查告警、授权、移送、证据及管理规则页面，含刷新/重新登录和 1280×720、1366×768、1440×900 布局。
- 时延：记录接入到研判、研判到任务创建、授权到下发、回执到展示、合格到交接创建的 P50/P95/最大值。正式时限在 P1 基线测试后冻结；不能把短信/设备真实时延当作本地模拟已证明。
- 每个场景输出：配置版本、输入清单、前置条件、预期/实际、关联 ID、状态时间线、断言结果、必要截图及已知限制。读取失败、接口缺失、模拟与真实清楚区分。
- 文档修改做链接及 `git diff --check`；实现阶段按受影响范围运行检查，不使用旧测试报告冒充当前通过。

## 10. 开发顺序、工作量与交付物

建议按业务切片推进：契约与迁移 → 后端服务和测试 → 管理配置 → 业务前台 → MQTT 场景 → 阶段验收。共用任务机制和异常处理先完成最小版本，再逐期扩展，避免先建庞大的通用流程平台。

| 工作包 | 依赖 | 粗估工作量 | 必交付 |
| --- | --- | --- | --- |
| 基线核对与契约冻结 | 无 | 3～5 人日 | 状态/接口差异、参数基线、关联清单、测试环境 |
| 第一期 P1-01～07 | 基线 | 12～18 人日 | 自动判断、通知衔接、自动观察、异常入口、S01～05/S16 报告 |
| 第二期 P2-01～07 | 第一期可信事实 | 10～16 人日 | 建议与授权衔接、回执/效果/急停闭环、S06～10 报告 |
| 第三期 P3-01～08 | 前两期执行与效果事实 | 15～22 人日 | 预授权、自动任务与移送、签收和补充材料、S11～17 报告 |
| 总体验收与交付 | 三期通过 | 4～6 人日 | 全链演示脚本、回归报告、部署/停用/恢复手册 |

总计约 44～67 人日，为基于现有代码的初步估算，不是固定交付承诺。按后端、前端与测试协同排期，实际工期取决于投入人员和接口稳定性；真实设备、短信供应商及处罚部门对接另估。每期发现公共契约或设备能力差异时调整任务，不通过跳过验收维持日期。

每一期提交：实现清单、接口与状态说明、新增迁移、自动测试、场景配置、验收报告和未接入项。页面现状更新 README，稳定用户约定更新适用 AGENTS；阶段结果写带日期的验收报告，不把本计划的目标能力写成当前能力。

## 11. 发布与回退

新能力按判断、通知、效果评估、自动执行、自动移送分别控制开关，默认先在隔离环境启用。预授权与真实通道单独控制，不能跟随某个“总自动化”开关同时开启。

回退优先停用新动作派发，保留在途任务的回执接收和对账、人工接管、急停及历史读取。不能只停调度而让已执行设备失去跟踪，也不能通过删除任务回退。数据库采用向前兼容迁移，历史授权、审计、交接快照和证据保留。

最终交付可声明“MQTT 模拟业务闭环通过”的条件：所有必测场景通过，输入来自实际接入链，过程由后台自动/授权用例产生，回执与效果独立核验，刷新和重启结果一致。不得据此声明真实飞手已通知、真实设备反制有效或真实处罚已办结。
