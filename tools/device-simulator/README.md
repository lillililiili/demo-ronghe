2026-10-12 并发修复：实时采集与接入调测可同时连接同一 TCP 模拟端口；每个实例最多 8 个客户端，登录、收包及 RTK 订阅相互独立，调测断开不影响持续采集。停止、登录失效或账号切换关闭本实例全部连接。手动模式仍不登记设备；18 项 TCP 回归通过，含两模式并发、端口探测、无效登录隔离、停止重启和连接上限。真实设备的多连接能力须按厂家协议另行验证。

## 独立原生 TCP 雷达（2026-10-12）

## 演示告警要两路来源（2026-10-06）

平台对只有一路来源的目标把握不够：任何一台设备单独上报（雷达、融合感知箱、TDOA、5G-A 都一样），或只经规范化观测入口上报时，融合置信度 0.65，低于合法性研判门限 0.75（演示值），结论只能是“不可判定”并转人工复核，不出告警；研判页写明“只有一路来源（可信度 65%），达不到 75%”。两台及以上不同设备同时看到时为 0.8（三路及以上更高），可以研判出违规并告警。2026-10-08 起雷达、融合感知箱单独上报也按一路算（CDX-P04），以前按两路算、会直接告警。

- 地图上画的目标都带高度基准（默认海拔 AMSL），一律走规范化观测入口，只算一路。要演示告警，在目标的“辅助上报设备”里再选一台雷达、TDOA 或 5G-A：主设备仍走规范化入口，辅助设备照常发 MQTT 目标报文（离地高度与规范化观测一致），不再从规范化入口重复报，平台按同一序列号合成一个目标、两路来源。辅助设备的协议报不了这类目标时（如气球），它也走规范化入口。
- 全量场景的 8 架无人机由 TDOA（规范化观测）和雷达（MQTT）两路上报。
- 全量场景第 120 秒的临时管制区版本更新保持原名称和归属：平台要求版本更新不改名、不改归属，改名会被拒（409），整批在第 2 分钟停下。

## 全量关联场景（2026-09-30）

2026-10-06 多设备观测修正：规范化观测按目标选择的主设备、辅助设备分别登记来源和上报，每路保留设备名称、场景设备编号及平台来源/设备关联；同一目标跨设备保持相同目标编号、无人机序列号、观测时间和高度基准，交给后端实际关联融合。只计算支持目标观测的雷达、TDOA、5G-A，未选设备及光电、气象、反制设备不凭配置数量计为目标来源。设备停止心跳或处于离线窗口时停止该路观测，恢复后沿用原来源；目标静默或通知后停报同时停止所有关联来源。

模拟器的“回读平台数据”支持多个规范化来源，并保留旧批次单来源回读。系统融合及告警阈值未改：本次联调中双源为 80%、单源为 65%；这取决于后端当前配置，不在模拟器写死。Python 服务需重启后重新登录、启动场景才能载入新逻辑，刷新网页不能替代服务重启。只选择主设备的目标仍按单源上报；共同监测时需为该目标选择支持目标观测的辅助设备。

2026-10-06 修正：气象类别只提交场景中的气象观测和天气预报，不再自动写入固定的大风、雷雨、低能见度三条风险。气象风险由平台已配置的预报规则按实际输入判断；直接 QA 风险输入和旧预设风险不进入业务地图、风险列表及对应导出，原记录保留追溯。

启动本机模拟器后打开 `http://127.0.0.1:8766/`，先连接本机业务后端，再点击地图下方“配置全量场景”。可选择无人机正常与异常飞行、单鸟与鸟群、未知/识别中目标、气球、人员、车辆、船舶、遥控器、气象、五类空域及设备异常，并选择现有飞手、计划来源绑定和通知回执策略（不选时任务带上模拟飞手和模拟报送单位，平台自动建档并关联）。点击“生成完整草稿”后，可在地图中编辑目标、轨迹与来源；“完整资料与接口字段”可编辑整份场景 JSON。确认草稿后点击“一键启动全量场景”，等待运行状态进入“运行中”，再用“回读平台数据”核对设备、计划、空域、目标、轨迹点、气象、研判和告警。启动请求进入准备阶段不表示业务链路已经通过。

## 全链路实时收发（2026-09-30）

入口仍为 `http://127.0.0.1:8766/`，连接本机 `8081` 后端。新版服务加载后，地图下方显示“实时收发”。如提示尚未加载模块，须重启 Python 服务；刷新静态页面不能替代重启。服务重启后重新登录，收发不会自动恢复。

1. 打开“收发模式设置”，选择正常、异常或混合模式。通知接收与模拟反制设备默认启用；运行多久只在页面顶部的“运行时长”选一次（2026-10-13 起，“收发模式设置”里不再有第二个运行时长）。反制设备在“收发模式设置”里选所属单位和区县，不选时跟随模拟器连接的单位与区县（平台里已启用的本机回放连接 local-lingyun-replay，登录后第一次启动会去平台上查；后台管理端已不再有设备数据连接页面，这条连接要开发人员在平台里建好），不需要模拟计划，也不自动授予反制权限。
   反制设备登记时带上位置，融合感知页才能画出它的“作用范围”：默认放在场景里第一台雷达的位置（现场融合感知箱里雷达、光电、反制装在一起），场景里没有雷达时在“收发模式设置”里填反制设备经纬度。平台上这台设备已经有位置的不改，要改到管理端“设备管理”。状态行“TCP … / 位置 …”显示平台上的实际位置（2026-10-08，新-4）。
   飞手短信、飞手电话和“通知上级”三条通道不用另配：接收端第一次连上平台时，平台把还没配过的这三条接到模拟接收端（2026-10-08，D-1 自动配）。处罚移送发给哪个单位，在“收发模式设置”的“处罚接收单位”里勾选，保存后马上生效：勾一个时反制完成后自动移送，勾两个以上时要人选，一个不勾时平台提示管理员去配。单位先在管理端“单位管理”里建好。
2. 点击“开始模拟”先做一次开始前检查（见文末“2026-10-13 选流程弹框与开始前检查”），通过后同时启动所选接收端与 MQTT 场景；只想接收通知和设备指令时用“启动接收端”。本地后端需加载 `local,qa`，保留现有录音配置及数据库连接，不能混用 `8767/18091` 隔离服务。
3. “暂停发送／停止场景上报”只控制场景；“停止全部收发”同时停止场景、通知接收和 TCP 监听并注销接收租约。退出网页不会停止任务。修改模式前需停止全部收发。

正常模式以运行副本消除设备离线、故障和短信后停报设定，保留业务风险和原轨迹；原场景另存 `source-scene.json`，不覆盖旧批次。异常模式沿用设备故障／离线窗口，可配置各通知渠道失败、超时、不回执和电话未接通／仅接通；混合模式保留正常设备指令并允许各渠道配置成功、失败、延迟、不回执或轮换结果。指令“不回执”不执行光电及四通道写指令；四通道“状态不变”返回实际未变化的模拟状态，光电仍正常。不得把通知成功、停报或指令发送确认视为飞离或设备执行完成。

四通道设备端仅监听 `127.0.0.1:10006`，支持协议 `0x10–0x13`、二进制和 ASCII Hex，端口占用报错，不切换端口。新启动模拟继电器全部关闭；停止模拟器后的本地归零不作为平台已核查停机的回执。

通知接收器每 0.5 秒取请求、每 5 秒续租，租约 30 秒，默认模拟电话播放 3 秒。每条消息保存首次接收时的处理模式与播放时长，切换配置或重启不改变该消息结果；2026-10-13 起平台取消短信送达后3秒、电话播放完成后10秒的固定观察等待，仍检查有效位置、回执及反制资格；2026-10-16 起启用的反制规则全部满足且业务校验通过时自动发起，否则由有权限的人发起。收件箱包含短信、电话、风险、处罚、计划反馈、设备运维六类权威历史；运维通知回执不代表设备恢复。设备运维通知自 2026-10-05 起由后台直接写入运维待办，不再发到接收程序，收件箱里的设备运维记录都是此前的历史。

电话通知使用后台当前选用的 WAV 原始字节。接收器校验消息里的录音编号、SHA-256 和 Base64 内容后，把文件落到 `.data/realtime-notifications/recordings/<录音编号>.wav`；`state.json` 与 `events.jsonl` 只记录相对文件路径、字节数和哈希，便于核对实际收到的文件而不重复保存音频正文。模拟器只负责接收、保存并按配置产生接通／播放回执，不代表真实电话外呼。

本地接口：`GET/POST /api/realtime/config`、`GET /api/realtime/status`、`POST /api/realtime/control`（`action=start|stop_all`）。配置字段为 `mode`、`notifications_enabled`、`countermeasure_enabled`、`countermeasure_scope`（`单位编号|区县编号`，可空）、`command_mode`、`play_seconds`、`outcomes`；旧设置文件里的 `countermeasure_plan_id`、`continuous` 读入时丢弃。文件只保存模拟配置；登录与 MQTT 凭据仍仅驻内存。`start-realtime-workers.ps1` 调用统一接收控制，不再另启旧设备保活进程。

主进程与单独启动的接收器共用同一操作系统锁，防止重复回执；独立 `device_presence.py` 见到统一控制会停止保活，不会在场景停止后恢复旧设备。实时模式禁止数据库 seed 配套，计划、空域和天气使用已有受权接口。

本轮代码验证：Python 132 项、Node 43 项通过；四通道测试使用真实本机 TCP socket。实际 `8766/8081` 重启被自动审批阻止，尚未完成新进程五分钟全链路验收，不能用单元测试或首页 HTTP 200 代替。完整状态见后台仓库 `docs/designs/2026-09-30-realtime-simulator-delivery.md`。

## 启动

```sh
python3 tools/device-simulator/server.py --port 8766
```

打开 http://127.0.0.1:8766/ 。需 Python 3.9+、Node.js 及业务前台已有依赖；MQTT 使用现有 `paho-mqtt` 2.x，未新增项目生产依赖。启动时自动构建共享地图入口。

地图读取当前业务前台的同一配置、PMTiles 数据包、影像与配色。默认地图服务为 `http://localhost:5173`，需保持业务前台地图服务运行；端口变化时使用 `--map-origin http://localhost:实际端口`。地图资源仅经本机同源代理读取，保留 HTTP Range 206，不复制整份地图包；读取失败显示错误和重试入口。

启动终端需保持运行。若页面提示“模拟器服务未连接”，重新执行上述启动命令；页面会自动恢复状态读取。重启后在“登录系统”重新登录一次，历史批次保留且不会自动续发。提交操作时断连表示结果未知，先恢复连接并核对运行记录，再决定是否重新操作。

默认使用实时模式，不接受 `--database` / `--schema`；计划与空域资料通过既有资料输入入口提交。只接受回环 API 与已启用、source_mode=replay 的本机 MQTT 连接；不能用于现场/生产环境。

旧地图场景需要自动配套计划和空域时，显式选择 `--isolated-qa-scene`。仅允许 `stage456_verify_*` 测试库及 `monitor_events_<32位小写十六进制>` schema，并须使用 8766 以外的端口及共享 `.data` 目录以外的独立批次目录：

```powershell
python tools/device-simulator/server.py --isolated-qa-scene --port 18767 --database stage456_verify_qa0928r10 --schema monitor_events_替换为本次fixture的32位标识 --container 替换为测试数据库容器 --data-dir tools/device-simulator/.data-qa --map-origin http://localhost:5173
```

隔离场景模式保留原场景时长、故障/离线窗口及目标通知后行为，不启动实时通知接收器或本机反制 TCP 接收端。页面明确显示模式，实时收发设置与按钮禁用；仍可开始、暂停、继续、停止场景上报并回读系统结果。既有账号权限、管理员 seed 限制与 loopback broker 身份校验保留，错误参数在服务启动前拒绝。

每次 `psql` 只搜索指定 schema，禁用 `psqlrc` 覆盖，业务表不存在时直接失败；PostGIS 的 `ST_GeomFromText` 须安装在 `public`。默认容器为 `deploy-db-1`，用 `--container` 指定实际测试容器。启动不新建 schema，每批在创建批次及配套写入前核对当前 API 的 broker UUID。底层 `Prerequisites` 未指定 schema 时仍保留原默认查询行为；CLI 隔离模式必须显式指定 schema。

## 怎么操作

1. **连接设置**：填现有系统 API（本机为 `http://127.0.0.1:8081/api/v1`）、账号和密码。读取后台 `local-lingyun-replay`；如 broker 需要认证，另填 MQTT 用户名密码。凭据仅保存在进程内存，不写场景、日志或浏览器存储。计划/区域受控 seed 只允许测试系统管理员。
2. **地图编排**：地图上方分为“设备与目标”“航线与区域”“计划与气象输入”；左侧按任务显示对象，右侧编辑当前对象。风险列表默认收起，可通过“展开列表”配置。在系统真实地图上拖动、缩放，放置设备组（气象、5G-A、光电、TDOA、雷达），修改数量；绘制目标轨迹、计划航线与限飞区域。点击左侧对象定位并在右侧应用设置；“全览”回到当前场景范围。设备经纬度使用 WGS84，单台、追加、整组移动均保留。
3. **风险场景**：勾选本次启用的风险配置，配置对应的飞行计划或空域依据。目标输入负责目标类别、位置/轨迹、观测高度、高度基准、鸟群数量、来源设备/通道和上报时序；风险输入不再填写这些观测事实，也不发送风险结论。目标与来源设备由模拟目标的设备观测生成，平台回读后按目标位置、航线、空域和时间规则自动判定；设备离线、设备故障场景才直接配置设备。目标有有效来源设备时，即使没有风险行也可上报；取消风险勾选不会停止该目标观测。组内支持协议的设备仍上报正常心跳。
- 显式选择的 `transport` 在保存、导出、导入和启动时保持不变。MQTT 目标未声明高度基准时保持未知，不自动补为 AMSL；原始协议 A 高度仍按该协议解析，不因为场景填写 AMSL 就变成已知海拔高度。AGL 与 MQTT 不兼容时提示手动选择规范化观测，不自动切换。旧场景未填通道时，声明 AMSL/AGL 的目标及气球沿用规范化观测默认，其余沿用 MQTT；规范化观测旧场景的默认 AMSL 保持兼容。
4. **启动 MQTT 模拟**：冻结场景快照，复用或幂等注册 replay 设备与本批次资料；设备条目的可选 `coverage` 是静态覆盖档案（`circle` 需 `radiusM`，`sector` 需 `rangeM/azimuthDeg/fovDeg`，两者都需 `sourceLabel`），只在注册后通过设备覆盖配置接口写入，不进入 MQTT 心跳。未声明的设备不覆盖已有台账配置。然后定速沿轨迹发送。运行 30 秒至 20 分钟后结束；暂停停止全部上报、继续沿原模拟进度运行；停止等待在途发布退出。关闭网页不停止 Python 进程内的运行任务。
5. **运行记录 → 回读系统结果**：分别查看 Broker PUBACK、后台设备事实、本批次目标、研判与告警。空结果不补成功，读取失败保留错误。源设备通过 `fusion_device_id` 对应目标 `source_links.device_id`。
6. **导出场景 / 导入场景 / 导出本批次**：场景可复用；批次导出包含设备/计划/区域映射、最近发送记录和系统回读。完整报文保存在本机 `.data/<batch>/events.ndjson`。

运行时锁定编辑器；停止后可以修改。保存场景仅保存编辑草稿，不会启动发送。未完成地图绘制时不能启动。

## 数据流与保护

- 当前设备台账同步（2026-10-13）：当前场景所有设备成功登记后、开始报文前，完整分页读取平台设备；以当前平台 ID、外部身份、MQTT 绑定、同 Broker、单位区域和模拟器来源核对，逐台停用并删除已退出场景的旧设备。后台和地图继续共用台账，历史不删。空场景不自动批量清空，分页不完整、身份冲突、权限不足或版本变化均显式失败并写明设备编号；部分成功不冒充全部成功。再次准备相同场景不新增设备。2026-10-14 起（用户确认方案 A）：仍有未结束工作（未完成指令、调测、光电跟踪、反制执行、急停待核查）的旧设备先经 `GET /devices/{id}/catalog-blockers` 查出，不停用、不退役、不让启动失败，运行记录写明哪台、为什么，处理完后下次启动再整理；停用后才变忙的会重新启用并同样说明。本场景要用、以前被退役或停用的模拟设备，启动时经 `POST /devices/restore-simulated` 恢复成同一条记录（历史保留，运行记录列出恢复了哪些），不用再换新编号；平台只恢复本模拟器登记、身份逐项一致的回放模拟设备，真实设备不恢复。旧版平台没有这两个接口时退回原做法。系统预置和其他来源不纳入自动清理，本轮按用户授权经原接口一次清理；验收保持 `app.dev-seed.enabled=false`。
- 设备注册：现有 `POST /api/v1/devices/onboard`，source_mode=replay。设备编号和外部身份按场景里的设备固定为 `map-sim-<类型>-<设备 id>`，同一场景的每个批次、服务重启后都复用同一台设备和同一个 MQTT 绑定；只有目标、计划、区域等批次资料随批次新建。全量场景的规范化观测源和气象站同样按单位区域、名称和位置复用（`map-sim-source-*`、`map-sim-weather-*`），只有改了位置才登记新的一台。
- 旧批次设备清理（2026-10-06）：2026-10-05 以前的版本每批按“批次号-序号”登记一套设备（如 `sim-1004093015-a1b2-3`），批次结束后这些设备一直心跳超时，设备监控里堆积离线设备和 HIGH 设备异常。先用有设备运维权限的账号列出：`python3 retire_legacy_devices.py --account admin1`（密码从环境变量 `SIM_PLATFORM_PASSWORD` 读取，未设置时交互输入；`--api` 默认本机 8081）；核对清单后加 `--apply`，逐台经设备接口先停用、再删除，版本校验、删除原因和审计都由平台记录。只处理同时符合旧批次编号、模拟器厂家/型号、replay 和模拟标记的设备，`map-sim-*` 稳定设备和人工录入的设备不会动。删除后该设备未关闭的设备异常不再出现在异常队列和统计里，原记录保留；仍有未完成指令或调测任务的设备会被平台拒绝删除，脚本列出原因并继续处理其余设备，处理完这些任务后重跑即可。
- 首帧保护（2026-09-30）：注册后先通过设备协议状态接口核对本批设备绑定，等待所有设备的后台连接及订阅确认，再开始计时和发送心跳、目标报文。等待上限 30 秒，失败或取消不开始发送；运行记录保存等待、就绪时间，历史缺失报文不补造。Broker 的 PUBACK 仍需与后台回读对账，不能单独证明业务已接收。
- 雷达、5G-A、TDOA：复用 `LINGYUN_MQTT_V8_6` 工参和 SenseData 契约。QoS 1、retain=false；目标与批次身份固定，观测时间随实际发送更新，按速度和折线距离推进，终点停留，不循环瞬移。鸟群按数量生成独立观测编号、固定小范围编队偏移。
- 光电：`EO_EDGE_MQTT_20250826` HeartBeat，以及真实订阅下发主题后的 BeginTracking / EndTracking / CameraStatus 模拟回执。匹配系统当前任务后才执行；默认开启本机 TEST VIDEO 水印测试流，不表示现场实拍。
- 离线：时间窗内停止该设备所有上报，恢复后正常上报；系统按自身超时阈值判离线。故障：协议 A workState=2，窗口结束后恢复原配置。
- 设备健康（2026-10-08，新-11）：协议 A 心跳不带健康码，平台里模拟设备的健康原来一直是“未知”，设备运维的恢复核验过不了。现在设备开始上报、停发或暂停后恢复上报、故障开始和结束时，模拟器先经 `POST /local-interface-simulator/device-status` 报一条健康状态（正常：在线、良好、无告警；故障：异常、故障、有告警），再发这条心跳。2026-10-10 起状况不变也每 30 秒随实际心跳补报明确健康和告警，避免新心跳续期旧健康；停止心跳、离线窗口、暂停或停止批次期间不报；光电自 2026-10-11 起按登记的光电绑定、边缘节点和设备来源接收独立模拟健康输入；健康依据来自已验证的场景配置，不从光电工作状态推断。规范化观测来源不是设备，不报健康。该接口只在后台 local,qa 运行时开放，接口没开或账号无权限时本批不再报，运行记录留一条说明；其余失败随下一条心跳重试，连续 3 次失败后每 30 秒继续重试，状况改变时立即重试，不永久放弃。重复周期上报不刷屏；接口关闭或无权限时明确提示健康来源不可用。
- 计划/区域：全量实时场景使用授权模拟接口提交 replay 航线、计划与空域，不走数据库 seed。仅显式隔离 QA 模式沿用受控 seed，通过 PostgreSQL 事务新增 replay 配套资料，并先核对 broker UUID。完整场景快照在任何写入前落盘，不覆盖或删除旧记录。
- 计划、区域时段使用**运行当天 Asia/Shanghai**。普通场景遵守页面时间；“超出计划时段”按选择的提前/延后及分钟数，将该目标配套计划定位到本批次开始前后，实际生效时刻可从系统计划回读。

- 这不是平台规则引擎；不通过前端定时器生成系统告警、通知成功或反制成功。实际状态、合法性判定和告警均以系统回读为准。

### 速度上报修正（2026-09-28）

- 目标报文现在携带 `objects[].speed`（米/秒），按当前轨迹段计算；雷达和 5G-A 同时携带 `extension.speedX/speedY/speedZ`（东、北、上）。当前轨迹为等高运动，Z 轴为 0；TDOA 不套用雷达的三轴扩展。
- 位置与速度共用 `target_motion()`：转弯改变方向，到终点、单点轨迹或设定速度为 0 时上报 0。通知触发撤离后使用撤离轨迹及撤离速度；停止目标上报时仍不发送目标报文。
- 修复仅影响加载新代码后的新报文，不回填已完成批次。服务需重启才加载 Python 修改，重启后重新登录，历史批次保留且不会自动续发。
- 设备上报、设备指令接收、外部接口输入与通知输出的完整核对见 [模拟器收发完整性梳理](../../docs/模拟器收发完整性梳理-2026-09-28.md)。清单区分已修复、待补能力及既有只读约定；不代表真实设备能力全部通过验收。

| 类型 / 场景 | 当前能力 |
| --- | --- |
| 雷达、5G-A、TDOA | 注册、心跳、工参、无人机/鸟类轨迹、离线与故障调度 |
| 光电 | 注册、心跳、离线、真实 MQTT 订阅与匹配任务回执；默认开启带水印本机测试流。未知故障码不造码，指令保持超时 |
| 气象设备 | 保留地图布设；现有系统没有相应设备 MQTT 契约，明确跳过发送；不伪造温度、风速字段 |
| 无计划、偏离、限飞区、时间风险 | 发送实际观测及配套资料，结果由现有引擎判断；选中场景不保证产生某个结论 |

## 独立实时通知接收器（2026-09-29）

`realtime_notification_receiver.py` 独立运行，通过已启动且已登录的本机 8766 服务复用内存会话，无需保持浏览器打开，也不读取账号、密码或数据库。它读取平台实际出站请求并经 API 提交模拟设备回执；后端不得以本地 MOCK 定时成功替代本接收器。平台须已提供 `receiver_messages` 队列及 30 秒接收器租约；不满足时显示错误并停止续租。

## 2026-10-13 区域不再设时分

信号地图里选中区域后，「对象设置」不再有开始、结束时间。开始模拟时每个区域一律按北京时间当天全天（00:00 到 23:59）有效，场景里区域自带的时分（旧草稿、旧场景文件里的 start / end）载入时被忽略，不报错；飞行任务的起止时间不变。

原因：区域的生效时段决定平台是否把它当作生效空域（生效时间 ≤ 观测时刻 < 失效时间）。默认的 08:00 到 18:00 到了晚上就是已过期的区域，平台照收但判定悄悄不生效；在「空域下发」手动下发过一条（生效时间在 18:00 之后）后，开始模拟还会因「今天已下发到结束时间」被挡。要让某个区域只在某个时段生效，到「资料输入」里的「空域下发」手动下发（结束时间可空）。

开始模拟时，若该区域最近一次下发（或撤销）的生效时间已到当天结束（23:59）或更晚（例如手动排到了明天），页面提示说明那一条的生效时间和处理办法，不发请求。测试：`python -m unittest tests.test_fullchain tests.test_engine -v`，`node --test tests/test_airspace_drawing.cjs`。

`manifest.json` 中流程9只列默认 `flow-9-prediction-warning.json` 一条；入区文件 `flow-9-prediction-entry.json` 由后端固定映射读取，两者均为 `fullchain.acceptanceFlow=9`。清单不能替换为任意变式路径或外部文件；缺文件、场景编号不符或清单缺项/重复都会明确失败，读取不写盘，也不自动启动场景。
